# 全流程 · 把陌生项目跑成可追溯的测试闭环

> 读者：第一次接手这个仓库的人。
> 用法：S0 → S6 顺序执行。每个阶段都有 **输入 / 动作 / 输出 / 验收标准 / 失败回退**，验收不过就停在原地，别带着假前提往下走。
> 与 `SKILL.md` 五步的对应：S1=识别，S2=建库，S3+S4=执行并归因，S5=提缺陷，S6=复盘。

```
S0 立项 ──▶ S1 识别 ──▶ S2 用例库 ──▶ S3 执行 ──▶ S4 归因 ──▶ S5 提缺陷 ──▶ S6 复盘
   │           │            │            │            │             │
 时间盒      项目画像      用例条目     结果+退出码   五分类        缺陷单/复盘
```

---

## S0 立项与环境体检

**输入**：仓库路径；被测环境 URL（没有就明确写"未提供"）；本轮目标（三选一：摸底 / 回归护栏 / 上线门禁）；可用人天。

**动作**

1. 先定时间盒，默认 **3 天**：第 1 天只要求"一条用例打通全链路"，第 2 天扩到 smoke 面，第 3 天出结论与缺陷。
2. 跑体检：

```bash
python skills/qa-full-cycle/scripts/check_env.py --target-url http://localhost:8000
```

3. 写下半页"目标 / 范围 / **不做什么**"。"不做什么"至少一条（例：本轮不做 UI 兼容性矩阵、不做性能阈值）。

**输出**：体检结论 + 半页立项说明。

**验收标准**

- `check_env.py` 退出码 `0`；若有 `WARN`，每条都知道"为什么可以接受"。
- 立项说明里能读出一句可判定的话，例如"3 天内给出该服务订单域 20 条用例，其中 P0 全部自动化"。

**失败回退**

| 现象 | 回退动作 |
|---|---|
| 缺 pytest / httpx | `python -m pip install pytest httpx`，重跑体检 |
| Python 版本偏低（<3.10） | 换解释器或建 venv，**不要**靠改脚本来兼容 |
| 被测环境起不来 | 本轮降级为"静态识别 + 契约级用例"，结论里明写"执行层未验证"，不许用 mock 结果充当实测 |
| atf 不可用（正常，本仓库不含 atf 实现） | 不影响 S0；S3 会给出替代路径 |

## S1 识别项目

**输入**：源码树 + 运行方式。

**动作（每步限时 15 分钟，不许陷进读代码）**

1. **技术栈判定**：按下面的表扫文件，扫到就停，不要逐个依赖读版本。

| 看到的文件 | 结论 |
|---|---|
| `pyproject.toml` / `setup.py` / `requirements*.txt` | Python 项目、依赖清单、能否 `pip install -e .` |
| `package.json` / `pnpm-lock.yaml` | 前端存在与否、能否独立起 |
| `Dockerfile` / `docker-compose.yml` | 环境启动的**首选**方式（比读 README 可信） |
| `pytest.ini` / `tox.ini` / `conftest.py` | 已有测试约定（testpaths、markers、fixtures） |
| `.github/workflows/` / `.gitee/` / `Jenkinsfile` | 既有 CI 入口与**既有门禁**（别重复造） |
| `migrations/` / `alembic/` | 数据模型与**状态机线索** |
| `openapi.json` / `swagger.yaml` / 路由注册文件 | 接口契约，L3 用例的原料 |

2. **可测面盘点**：入口（HTTP 路由 / CLI / UI 路由 / 定时任务 / 消息消费）、数据层、外部依赖（支付、短信、第三方 API）。
3. **存量测试盘点**（只收集不执行）：`python -m pytest --collect-only -q | tail -5`，拿到测试文件与用例数；没有测试也要记下"0"。
4. **风险定位**：只看三处——README 的功能描述、CHANGELOG 最近 10 条、历史缺陷/issue 标题。找"钱 / 权限 / 状态机"三类规则，这三类错了代价最大。
5. **选层**：按"能在最底层证明问题就在最底层断言"分配。典型比例：L1 单元 5 : L3 接口 4 : L4 E2E 1。

**输出**：一页项目画像（技术栈 / 可测面清单 / 风险 Top3 / 建议层级与首批 5 条用例 / 明确不可自动化面及原因）。建议落在被测仓库 `docs/qa-onboarding.md`。

**验收标准**

- 能回答："最值钱的一条用例是哪条，它属于哪层，为什么不是更底层？"
- 至少指出 1 个**不可自动化**的面并给原因（如"依赖真实支付回调，无沙箱"）。
- 画像里没有"待定"字段。

**失败回退**

- 项目装不上/起不来：转入"契约与单元层静态用例"，画像里标 `执行性：未验证`，并把阻塞项写成一条 issue。
- 存量测试一大堆但全红：先只跑 `--collect-only`，把"能不能收集"当第一个结论；红线根因未明前不做覆盖评估。
- 无法判断技术栈（多语言单仓）：按目录切开，只挑与本轮目标相关的一个子目录做画像。

## S2 建 / 维护用例库

**输入**：S1 画像 + 需求/规则/历史缺陷。

**动作**

1. 复制 `assets/case-template.yaml` 生成条目；字段含义与约束看 `references/case-library-spec.md`。
2. ID 用 `模块-序号`（`CART-004`），**只增不改**：删掉的用例保留 `status: deprecated`，编号永不复用。
3. 判定标准必须可断言。写不出可断言的（"显示正常""性能可接受"），这条不进库，进"待澄清"清单——那通常是需求缺陷。
4. 首批只做 5–15 条 smoke：P0 覆盖核心链路，每条能独立跑。
5. 状态先 `manual`；接上代码后改 `automated` 并填 `automated_by`（必须能解析到真实测试）。

**输出**：用例库文件（YAML 或 CSV，字段按规范）+ 一条"待澄清"清单。

**验收标准**

- 必填字段无空缺；ID 无重复；`status=automated` 的每一条 `automated_by` 都能解析。
- 至少 1 条覆盖状态机（如订单取消/重复提交幂等），至少 1 条覆盖权限或金额。
- 用例数与"待澄清"数的比例被记下来（后续复盘的基线）。

**失败回退**

- 断言写不出来 → 降级为探索式用例，标 `status: manual` + 在 `title` 里写明待确认点。
- 需求方给不出规则 → 用"当前实现的观测值"建基线，但必须在 `requirement` 字段注明"基线来自实现，非需求"，这类用例不得进 P0。
- 用例爆炸（>50 条待写）→ 只留 P0，其余进 backlog，别一次写完。

## S3 执行

**输入**：用例库 + 可用环境。

**动作**

1. 先看它要干什么（不执行）：`python skills/qa-full-cycle/scripts/run_cycle.py --tag smoke --dry-run`
2. 真跑：`python skills/qa-full-cycle/scripts/run_cycle.py --tag smoke --shards 2`
3. 保留结果文件（JUnit XML）与失败用例清单，作为 S4 的唯一证据源。

**输出**：退出码 + 通过/失败清单 + 结果文件。

**验收标准**

- 退出码语义明确（`0` 全绿 / `1` 有失败 / `2` 体检没过 / `3` atf 不可用）。
- 失败项 100% 能落到用例 ID；没有"无名失败"。
- **确定性抽查**：任选 2 条用例连跑两次，结果一致（否则进隔离区，见 S4）。

**失败回退**

| 现象 | 回退动作 |
|---|---|
| `run_cycle.py` 退出码 `3`（atf 不可用） | 走替代路径：`python -m pytest -q --junitxml=runs/junit.xml`，然后**人工**把 nodeid 映射回用例 ID；报告里注明"未经 atf"，不得声称跑通了全流程 |
| 个别用例因环境挂 | 先修环境；修不动就把该用例标 `skipped` 并写明原因，**不许**改成通过 |
| 大面积超时 | 先用 `--shards 1 --dry-run` 看调度是否切错；仍超时则缩减本轮 smoke 面并在结论里写清 |
| 同一用例时绿时红 | 进隔离区（`tag: flaky` + 期限 ≤30 天），当轮结论里明确排除，不许静默重跑 |

---

> **本仓库已提供一键执行**：python -m atf e2e --filing mock --tracker both
> （或 Windows 下 scripts/run_e2e.ps1）会把「重置 → 起服务 → 分层执行 → 归因 → 缺陷 → 报告」一次跑完；
> 全部配置项与验收标准见仓库 docs/15-runbook.md。分步执行时仍可用下面的命令。

## S4 归因

**输入**：S3 的失败清单 + 每条用例的判定标准 + 现场证据（日志/截图/trace/响应体）。

**动作**：每条失败先分类，再决定去处。分类只有五种，必须选一个。

| 类别 | 判据（看什么） | 处置 | 禁止动作 |
|---|---|---|---|
| **产品缺陷** | 实测值与需求/契约不符，且证据可第三人复现 | 进 S5 提缺陷，附用例 ID | 顺手改断言让它过 |
| **用例缺陷** | 断言与当前需求/契约不符；或断言在测实现细节（mock 调用次数） | 改用例 + 在复盘里记一条"断言在用例外" | 偷偷改基线 |
| **环境问题** | 环境不可达 / 版本不一致 / 缺种子数据 / 依赖服务 5xx | 修环境，重跑；结论标注"环境所致" | 把环境问题算进产品缺陷率 |
| **数据问题** | 仅特定数据触发（脏数据、共享账号被改、时区/金额精度） | 造数据或用例自带 fixture；排查是否漏覆盖真实分布 | 用"换条数据能过"结案 |
| **flaky** | 同输入不同结果、依赖时间/顺序/并发 | 隔离区 + 限期修；计数进 flaky 率 | 重跑三次取绿 |

**输出**：归因表（用例 ID / 类别 / 证据 / 处置 / 负责人）。

**验收标准**

- 失败 100% 有类别，没有"待定"超过 1 天。
- "用例缺陷"占比 > 30% 时，必须单独出一条动作：本轮断言整体过弱，需要重新对齐需求。
- flaky 率与上一轮可比（同口径：flaky 次数 ÷ 执行次数）。

**失败回退**

- 判不出来 → 标"待复现"，附**最小复现命令**与一次失败/一次通过的日志对比；不许猜类别。
- 证据不足（无日志、无响应体）→ 先补证据能力（加 trace、加响应体转储），再回到 S4；这是工程债，记入复盘。

## S5 提缺陷

**输入**：已归因为"产品缺陷"的失败项 + 证据 + 用例 ID。

**动作**

1. 先出 dry-run，字段完整、可直接贴进工单（约定见 `references/bug-integration.md` §6）。
2. 算指纹，查重窗（默认 30 天）内同指纹已存在 → 只追加"再次复现于 <运行ID>/<日期>"评论，不新建。
3. 凭据齐全且完成前置检查（只读连通性 + 字段权限 + 沙箱 canary）后，才允许 `--execute` 真提交。
4. 记录 工单号 ↔ 用例 ID ↔ 运行 ID 的映射，供 S6 与后续回归。

**输出**：缺陷单（或 dry-run 报文）+ 映射表。

**验收标准**

- 标题符合 `[模块] 现象（用例 ID）`；描述六段齐全（环境/步骤/期望/实际/证据/用例 ID）。
- 无重复单；复现步骤能被第三人在 5 分钟内执行。
- 未做真实验证的地方，措辞为"未验证"，不出现"已对接/已验证"。

**失败回退**

- 无凭据：只交 dry-run，交付说明写清验证路径与剩余风险。
- 字段不被接受（如 severity 选项不同）：以服务端返回的字段元数据为准，修订映射表并回写 `references/bug-integration.md`。
- 提交失败但已建单：先查重再重试，避免"提交超时其实成功"造成重复单。

## S6 复盘

**输入**：本轮用例库变更、归因表、缺陷单、执行耗时。

**动作**

1. 用例库做"删 / 改 / 留"决策（判据见 `references/case-library-spec.md` §5）。
2. 挑 Top3 失败根因，每条给**一个**可验证动作（补哪条用例、改哪类断言、动哪条门禁）。
3. 明确写"本轮不做什么"及其理由。
4. 出一条"下一轮 3 天计划"，把 S1 画像里"不可自动化面"重新评估一次。

**输出**：复盘记录（建议套用本仓库 `docs/11-templates-and-checklists.md` §8 的复盘模板）。

**验收标准**

- 每个动作有负责人、截止、验证方式；动作数 ≤ 5（多于此必含水货）。
- 产出"删 N / 改 M / 隔离 K"的量化结论。
- 若出现"加强测试意识""提高覆盖率"这类无法验证的动作，视为复盘失败，重写。

**失败回退**

- 只有泛泛结论 → 回到 S4 的归因表，用数据顶替形容词。
- 动作推不动（没人认领）→ 升级为管理层视角的问题，写进立项说明的"不做什么"，别在复盘里假装已解决。

## 演练路径：用真实开源项目走一遍（Wagtail 全栈 CMS，已实测）

**为什么选它**：真实全栈（Django 服务端渲染 + 后台 SPA），`pip install` 即可跑、无需 Node 构建，
业务流完整（创建内容 → 发布 → 前台可见），管理后台是真实复杂 UI——正好练 S1 的风险定位与 S4 的归因。

**本仓库已把这条路径做成可复用实验**（推荐直接用，省掉环境折腾）：

```bash
cd labs/07-real-project
./bootstrap.ps1                       # 装依赖 → migrate → 灌种子 → 建本地账号（幂等）
cd app && python manage.py runserver 127.0.0.1:8099 --noreload
```

等价的手工路径（想自己搭时参照）：

```bash
python -m pip install "wagtail>=6.2,<7"
python -c "import sys; from wagtail.bin.wagtail import main; sys.argv=['wagtail','start','demo','app']; main()"
cd app && python manage.py migrate && python manage.py runserver 127.0.0.1:8099
```

要点（都是实测踩出来的）：

- 站点在 `http://127.0.0.1:8099`；本地测试账号由 `manage.py ensure_qa_user` 幂等创建
  （默认 `qa` / `qa-pass-12345`，**仅本地 sqlite**，不是任何生产凭据）。
- 后台按钮常藏在折叠菜单（如 "More actions"）：先展开容器，再 `expect(...).to_be_visible()`，
  然后才点；直接点隐藏元素会等 30s 超时。
- Wagtail 的 slug 在标题 blur 时由前端生成：填完标题要 `blur()` 并等 `#id_slug` 非空再提交，
  否则得到"slug 不能为空"的校验错误。
- 成功判据用页面提示（如 `created and published`），**不要用 URL**——发布后跳哪一页不稳定。

**演练验收（按本 skill 的口径）**

| 检查 | 通过标准 |
|---|---|
| 环境 | `python skills/qa-full-cycle/scripts/check_env.py --target-url http://127.0.0.1:8099` 退出码 `0` |
| 用例库 | ≥12 条，覆盖内容页 / 导航 / 后台 / 发布链路；P0 全部可断言 |
| 分层 | 至少 1 条 L3（页面 200 + 关键结构）、1 条 L4（E2E：登录 → 新建 → 发布 → 前台可见） |
| 执行 | `run_cycle.py` 退出码 `0`；若 atf 缺失，用 pytest 替代并标注"未经 atf" |
| 归因 | 用一条演练用负向用例（如 robots.txt 缺失）跑出真实失败，并完成一次 dry-run 提缺陷 |
| 复盘 | 产出"删/改/留"清单与 1 条下一轮动作 |

**注错练习（S4 的关键训练）**：在本地把某条断言对应的实现改坏（不改断言），确认失败信息能直接读出
"期望 vs 实际"；再改回去确认恢复。做过一次，你才知道自己的断言是不是"看起来在测，其实什么都没测"。

**备选路径**：`django-oscar sandbox`（电商语义更强：catalogue / basket / checkout），
但需 clone 整仓并安装较多依赖；官方 `make sandbox` 在 Windows 无 `make`，
需手工等价三步，**作者未在 Windows 实测该等价关系**。

## 时间盒与反模式速查

| 阶段 | 默认时间盒 | 最容易犯的错 |
|---|---|---|
| S0 | 0.5 天 | 没定"不做什么"，导致范围膨胀 |
| S1 | 0.5 天 | 陷进读全部源码；忘了看 CI 里已有的门禁 |
| S2 | 1 天 | 一次写 80 条，全部断言过弱 |
| S3 | 0.5 天 | 环境问题当成产品缺陷 |
| S4 | 0.5 天 | 不分类直接提 12 个单 |
| S5 | 0.5 天 | 无凭据却声称已对接 |
| S6 | 0.5 天 | 动作不可验证（"加强测试"） |

> 一句话：**先跑通一条，再谈覆盖；先能追溯，再谈数量。**
