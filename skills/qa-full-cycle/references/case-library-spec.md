# 用例库规范 · 字段、状态机、绑定、覆盖率、巡检

> 目标：让"这条用例到底测什么、谁负责、有没有人跑、跑的结果算不算数"四个问题都有唯一答案。
> 适用：YAML 或 CSV 存储的用例库；字段名即为列名，前后端脚本都以本文件为准。

---

## 1. 字段表

### 1.1 核心字段（11 个）

| 字段 | 类型 | 必填 | 取值 / 格式 | 约束 | 示例 |
|---|---|---|---|---|---|
| `id` | string | 是 | `模块-序号`，模块大写字母/数字，序号 3 位补零 | 全局唯一；**永不复用**；一旦分配不得改名 | `CART-004` |
| `title` | string | 是 | ≤80 字，一句话 | 必须写成"在什么条件下验证什么"；不得以"测试/验证/检查"开头 | 会员折扣后金额低于门槛时满减券不生效 |
| `layer` | enum | 是 | `L1` `L2` `L3` `L4` `L5` | 与本仓库 `docs/01` 的分层一致；L5 仅性能/容量 | `L1` |
| `priority` | enum | 是 | `P0` `P1` `P2` | P0 只给资金、权限、核心链路、历史逃逸缺陷 | `P0` |
| `tags` | list[str] | 否 | 小写；建议取值 `smoke` `edge` `regression` `slow` `flaky` | 至少要有一个 CI 能选择的标签，否则这条用例永远不会被跑到 | `[smoke, regression]` |
| `requirement` | string | 是 | 需求号 / 规则号 / 缺陷号，多值用 `,` 分隔；确无出处写 `-` | 必须指向可查实体；写 `-` 的用例不得进 P0 | `RULE-R3,BUG-1042` |
| `status` | enum | 是 | `manual` `automated` `deprecated` | 状态机见 §2 | `automated` |
| `automated_by` | string \| null | 条件必填 | `仓库相对路径::测试节点` | `status=automated` 时必填，且**必须能解析到真实测试**（§3） | `tests/test_pricing.py::test_vip_below_threshold` |
| `owner` | string | 是 | 团队名或工号 | 不许为空、不许是"全体/所有人"；离职即失效 | `team-pricing` |
| `last_run` | date \| null | 条件必填 | `YYYY-MM-DD` | `status=automated` 时必填；不得是未来日期 | `2026-11-16` |
| `last_result` | enum \| null | 条件必填 | `pass` `fail` `skipped` `not_run` | 与 `last_run` 同生同死（一个有值另一个必须有值） | `pass` |

### 1.2 扩展字段

自定义字段一律加 `x-` 前缀（`x-quarantine_until`、`x-jira_key`），工具链必须忽略未知的 `x-` 字段而不是报错。不扩核心字段，避免规范漂移。

### 1.3 常见错填

| 写法 | 问题 | 改法 |
|---|---|---|
| `id: CART12` | 无分隔，序号不足位，无法排序与按模块聚合 | `CART-012` |
| `title: 测试购物车` | 没有条件、没有判定 | 购物车数量改为 0 时提交按钮不可用 |
| `requirement: 需求文档` | 指向不到具体条目 | `REQ-2026-118 §3.2` |
| `owner: 张三` 且已离职 | 无主用例 | 改用团队名，交接时整体迁移 |
| `automated_by: pytest` | 解析不到具体测试 | `tests/test_cart.py::test_qty_zero_disables_submit` |
| `status: automated` 但 `last_run` 为空 | 声称自动化却从未执行 | 首次真实执行后再改状态 |

## 2. 状态机

```
                 (建档)
                   │
                   ▼
   ┌──────────── manual ────────────┐
   │                │                │
   │       ①接上自动化               │ ③需求/功能已下线
   │                ▼                ▼
   │           automated ───────▶ deprecated  (终态)
   │                │
   └────────────────┘
        ②automated_by 解析失败 / 测试被删
```

| # | 迁移 | 触发条件 | 同一变更里**必须**同时更新 |
|---|---|---|---|
| ① | `manual → automated` | 已提交测试代码，且该测试至少成功执行 1 次 | `automated_by`、`last_run`、`last_result` |
| ② | `automated → manual` | `automated_by` 解析失败（文件/函数不存在）；或测试被删 | 清空 `automated_by`；`x-revert_reason` 写明原因与责任任务 |
| ③ | 任意 → `deprecated` | 需求取消、功能下线、被新用例替代 | `x-deprecated_reason` + `x-superseded_by`（若被替代） |

**硬规则**

1. **②是强制的，不是可选的**：只要绑定解析不上，状态必须立刻回退 `manual`。留着 `automated` 的悬空条目 = 假的覆盖率。
2. `deprecated` 是终态。要复活就**新建 ID**，旧条目留着做历史；不允许把 `deprecated` 改回 `manual`（否则报告口径会跳变）。
3. **`flaky` 不是状态**，是 `tags` 里的标签 + `x-quarantine_until` 日期。状态只有三个，避免状态爆炸。
4. 报告里任何"已自动化""已覆盖"的结论，只能来自 `status` 字段，不来自口头或截图。
5. `last_result` 只记录**最近一次真实执行**；不许手工改成 `pass` 让面板变绿。

## 3. 与测试代码的双向绑定

单向绑定必然腐化：代码改了没人改用例库。所以两个方向都要能被机器检查。

### 3.1 正向：用例 → 代码（`automated_by`）

格式：`<仓库相对路径>::<pytest 节点>`

| 形态 | 示例 | 解析规则 |
|---|---|---|
| 普通函数 | `tests/test_pricing.py::test_vip_below_threshold` | 文件存在 + 函数存在 |
| 类方法 | `tests/test_orders.py::TestCancel::test_cancel_twice_idempotent` | 文件 + 类 + 方法 |
| 参数化 | `tests/test_pricing.py::test_threshold[gold-100.00]` | 节点含参数时，只校验到函数级，参数由 `tags`/`requirement` 承载 |

解析实现（任选其一，CI 用一条 job 跑）：`pytest --collect-only -q` 抓全部 nodeid 做集合比对；或对文件做 AST 解析（不执行代码，更安全）。

### 3.2 反向：代码 → 用例

每个测试必须显式声明它服务的用例 ID，二选一：

```python
@pytest.mark.case("CART-004")
def test_qty_zero_disables_submit(): ...

# 或（不想注册 marker 时）
def test_cancel_twice_is_idempotent():
    """case: ORDER-012 —— 重复提交取消请求不得产生第二条取消记录"""
```

- 一个测试可以绑定多条用例（矩阵场景）：`@pytest.mark.case("PRICE-011", "PRICE-012")`。
- 一条用例只能有**一个**主 `automated_by`；需要多测试共同证明的，拆成多条用例，别搞一对多。

### 3.3 两类失配与处置

| 失配 | 定义 | 处置 |
|---|---|---|
| **悬空用例** | `status=automated` 但 `automated_by` 解析失败 | 立刻回退 `manual`（状态机 ②），开任务补测试；本轮报告中该条不计入自动化率 |
| **孤儿测试** | 测试代码里没有 `case:` 标记 | 建用例或删测试，二选一；不许"留着反正它能跑"——它不进入任何报告口径 |

### 3.4 校验时机与失败策略

| 时机 | 检查 | 失败后果 |
|---|---|---|
| 提交前（本地） | 改动的用例字段合法 + 本次涉及的 `automated_by` 可解析 | 提交者自己修 |
| CI（每次执行后） | 全量双向绑定比对 + 覆盖率统计更新 | 红灯，阻断合并；`flaky` 标签不能豁免此检查 |
| 季度巡检 | 悬空/孤儿清单清零 | 进复盘动作表 |

## 4. 覆盖率口径

**口径必须唯一、不可协商；允许争论"目标定多少"，不允许争论"怎么算"。**

| 指标 | 定义式 | 数据源 | 参考目标 | 用途 |
|---|---|---|---|---|
| 自动化率 | `count(status=automated) ÷ count(status≠deprecated)` | 用例库 | 项目自定；P0 要求 100% | 看"资产里有多少真能跑" |
| 绑定有效率 | `可解析的 automated_by ÷ count(status=automated)` | 校验脚本 | **100%**，低于即红灯 | 识别"假自动化" |
| P0 覆盖率 | `count(P0 且 automated 且 last_result≠not_run) ÷ count(P0)` | 用例库 | 100% | 门禁的唯一硬口径 |
| 孤儿测试率 | `无用例标记的测试 ÷ 测试总数` | 代码扫描 | < 10% | 识别"跑了但不被理解"的测试 |
| flaky 率 | `flaky 命中次数 ÷ 执行次数` | 执行记录 | < 5% | 决定是否隔离 |
| 需求覆盖 | `有 ≥1 条用例的 requirement ÷ 本轮涉及需求数` | 用例库 + 需求单 | 核心需求 100% | 与产品/需求对齐 |

**不要拿 LOC 覆盖率当交付指标**：它能到 90% 而一条断言都没有。它只适合当**反指标**——"这条核心链路连执行都没执行过"。

## 5. 季度巡检（删 / 改 / 留）

每季度对全量用例做一次决策，输出必须是"删 N / 改 M / 隔离 K"，不是感受。

| 判据 | 动作 | 留痕 |
|---|---|---|
| 连续 2 个季度未失败，且对应代码/功能已删除 | **删**（→ `deprecated`） | `x-deprecated_reason: 功能已下线 (PRD-2026-07)` |
| 需求变更导致用例已不成立 | **删** | 在需求单里回链用例 ID |
| flaky 率 > 5% | **改**（限期 2 周）或**隔离**（`x-quarantine_until`，≤30 天） | 隔离到期必须出区或被删，不许无限续期 |
| 断言过弱（无业务结论 / 只断言没抛异常） | **改** | 在复盘里记一条"断言在用例外" |
| 覆盖历史缺陷 | **留**，并在 `requirement` 标缺陷号 | 逃逸缺陷复审时作为证据 |
| 覆盖核心链路 | **留**，纳入 `smoke` | 门禁依赖 |
| 无 owner 或 owner 已离职 | **强制改 owner** | 无主用例数必须为 0 |
| 90 天未执行（`last_run` 过旧）且非 manual | **改**（接回执行）或**删** | 说明该层是否已被放弃 |
| 同一判定标准存在多条 | 合并为参数化一条，保留层级更高的 | §6 去重 |

**巡检产出**：`删 N / 改 M / 隔离 K` + 本季度用例总数变化与逃逸缺陷趋势的对照（两个数字放在一起看，才知道用例是变有效了还是变多了）。

## 6. 去重

### 6.1 判定

先归一化，再比对：

1. 小写、去空白与中英文标点；
2. 数字统一替换为 `#`（金额、数量、ID 都不该决定用例身份）；
3. 取 `(模块, 归一化 title, 归一化判定标准)` 三元组做键；判定标准存在 `x-assertion` 扩展字段里时以它为准。

三元组相同 → 重复。

### 6.2 边界

| 现象 | 是否重复 | 处置 |
|---|---|---|
| 同一逻辑，只是金额/数量不同 | 是 | 合并为一条参数化用例，`requirement` 写全 |
| 同一逻辑，不同层级（L1 与 L3 都测折扣） | 否 | 保留，但 P0 只标在能证明问题的最底层那条 |
| 同一接口，不同错误码 | 否 | 分开，`tags: [edge]` |
| 历史缺陷回归与常规用例判定标准相同 | 是 | 保留一条，`requirement` 同时写缺陷号与规则号 |

## 7. 提交前自检

- [ ] 新增用例的 `id` 未与既有冲突，且模块前缀与目录一致。
- [ ] `title` 里能读出条件与判定；`requirement` 指向可查实体。
- [ ] `status=automated` 的每一条，`automated_by` 我都刚验证过能解析。
- [ ] 代码侧加了 `case:` 标记，孤儿测试清单没有变长。
- [ ] 被我删掉的条目是 `deprecated` 而不是真的消失。
