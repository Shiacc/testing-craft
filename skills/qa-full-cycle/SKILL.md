# QA 全流程 · 陌生项目到可追溯的测试闭环

**定位**：把"跑过了"变成"说得清"。产物不是一堆通过的日志，而是**每条失败都能指到一条用例、每条用例都能指到一段代码、每个缺陷都能指回一次运行**。

---

## 1. 何时触发

**用**：

- 接手一个没接触过的仓库/服务，要在几天内给出"哪里该自动化、先做哪几条"的结论。
- 已有测试在跑，但说不清覆盖了什么、失败归谁、缺陷从哪来。
- 要把散落的 pytest/手工清单收敛成有 owner、有状态的用例库。
- 要把测试失败批量转成缺陷单，且不想被"同一现象提 12 单"埋掉。
- 一次发布/一轮回归之后要做复盘，需要证据链。

**不用**（走别的路径，别把流程套在单点上）：

- 只调一条用例、只修一个 flaky：直接改代码。
- 纯性能专项、容量规划：先有稳定功能用例再谈阈值。
- 平台选型、工具横评：本仓库文档层已覆盖，不属本 skill。

## 2. 五步流程

每步一句话说清"这一步只解决一个问题"，命令给的是**入口**，细节在 `references/workflow.md`。

| # | 步骤 | 一句话 | 命令 / 入口 |
|---|---|---|---|
| 1 | 识别项目 | 用清单式盘点回答"这项目有什么可测、最值钱的一条用例是哪条"。 | `python skills/qa-full-cycle/scripts/check_env.py --target-url <URL>` |
| 2 | 建/维护用例库 | 先落 5–15 条 smoke，字段齐全、判定标准可断言，跑通后再扩。 | `assets/case-template.yaml` + `references/case-library-spec.md` |
| 3 | 执行并归因 | 跑起来，并把每个失败先分类到"产品/用例/环境/数据/flaky"，再谈提缺陷。 | `python skills/qa-full-cycle/scripts/run_cycle.py --tag smoke` |
| 4 | 提缺陷 | 默认 dry-run 出完整字段供人复核，凭据齐全且通过前置检查才真提交。 | `assets/bug-template.md` + `references/bug-integration.md` |
| 5 | 复盘 | 只产出可验证的动作：删/改/留用例、改断言、动门禁，各带负责人。 | `references/workflow.md` §S6 |

**阶段编号对照**（两份文件用不同粒度，避免对不上）：

| SKILL.md 五步 | workflow.md 六阶段 |
|---|---|
| 1 识别 | S0 立项 → S1 识别 |
| 2 建/维护用例库 | S2 用例库 |
| 3 执行并归因 | S3 执行 + S4 归因 |
| 4 提缺陷 | S5 提缺陷 |
| 5 复盘 | S6 复盘 |

## 3. 三条铁律

违反任一条，这次流程的结论就不可信——不管日志多绿。

### 铁律 1｜无凭据必须 dry-run，且标注"未验证"

判据：没有禅道/Jira 的真实凭据、没做过只读连通性探测、或没在沙箱项目试过一条 canary，就只能出 dry-run 结果。
违反形态：把"按文档推断的字段映射"写成"已对接成功"；用假 token 试一次 401 后仍声称验证过。
正确动作：输出完整待提交字段 + 明确写 `未验证线上字段有效性`；把验证路径写进交付说明（见 `references/bug-integration.md` §8）。

### 铁律 2｜失败必须能追溯到用例 ID

判据：报告里任意一条失败，都能反查到用例库里的 `id`，以及 `automated_by` 指向的真实测试。
违反形态：报"3 个接口挂了"；失败项只有 nodeid 没有用例号；参数化用例失败后无法定位是哪组数据。
正确动作：执行前先确认绑定有效（`automated_by` 可解析）；映射不上就先补绑定，再下结论；宁可少报也不报无名失败。

### 铁律 3｜不得为变绿改基线、改断言

判据：断言改动只允许因为**需求/契约变了**且有出处，不允许因为"这次没过"。
违反形态：把 `assert payable == 90.00` 改成 `assert payable > 0`；把性能基线改成"最近一次的值"；把失败用例加 `skip`。
正确动作：失败先归因（S4 五分类）；确认是用例错就明写"用例缺陷 + 判定标准原文 + 修正依据"；确认是产品错就走提缺陷；**flaky 进隔离区，不许静默重跑**。

## 4. 产物清单

| 产物 | 落位 | 何时产生 | 验收口径 |
|---|---|---|---|
| 环境体检结论 | 终端输出 / `--json` | 步骤 1 之前 | 有 FAIL 就必须先修，不许跳过 |
| 项目画像 | 被测仓库（如 `docs/qa-onboarding.md`） | 步骤 1 | 能答"最值钱的一条用例 + 不可自动化面" |
| 用例库 | 被测仓库（YAML/CSV，字段见规范） | 步骤 2 | 每条必填齐全、ID 唯一、`automated_by` 可解析 |
| 执行结果 | `run_cycle.py` 输出 + JUnit XML | 步骤 3 | 失败项 100% 映射到用例 ID |
| 归因表 | 被测仓库 / 复盘材料 | 步骤 3 | 五分类占比可统计，无"待定"超期项 |
| 缺陷单（或 dry-run 报文） | 禅道/Jira 或本地 `dryrun-*.md` | 步骤 4 | 标题含用例 ID、指纹不重复、未验证处已标注 |
| 复盘记录 | 被测仓库 | 步骤 5 | 每动作有负责人 + 验证方式 + 截止 |

## 6. 常用命令

```bash
# 1) 体检（默认探测 http://127.0.0.1:8000；要求必须在线时加 --require-target）
python skills/qa-full-cycle/scripts/check_env.py --target-url http://localhost:8000
python skills/qa-full-cycle/scripts/check_env.py --json

# 2) 跑一轮（先看它会执行什么，不真跑）
python skills/qa-full-cycle/scripts/run_cycle.py --tag smoke --dry-run

# 3) 真跑
python skills/qa-full-cycle/scripts/run_cycle.py --tag smoke --shards 2

# 4) 提缺陷：先出 dry-run 报文，人工复核字段
#    凭据只从环境变量读，见 references/bug-integration.md §7
```

`check_env.py` 退出码：`0` 通过 / `1` 有硬性缺失 / `64` 参数错误。
`run_cycle.py` 退出码：`0` 全绿 / `1` 有用例失败 / `2` 体检未通过 / `3` atf 不可用 / `64` 参数错误 / `130` 中断。

## 7. 开工前自检

- [ ] 我知道这个项目的"最值钱的一条用例"是哪条，以及它在哪一层（L1/L3/L4）。
- [ ] 用例库里每条 `automated_by` 我都能解析成真实测试；解析不了的已回退 `manual`。
- [ ] 我准备好承认"这次有 3 条失败是环境问题"，而不是先把它们标绿。
- [ ] 提缺陷我默认走 dry-run，且知道无凭据时要写"未验证"。
- [ ] 复盘我准备了"不做什么"，避免会上变成许愿池。
