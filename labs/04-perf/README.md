# Lab 04 · L5 性能测试与阈值门禁

> **一句话**：性能测试的产物不是报告，是**退出码**。超过阈值就 `exit 1`，CI 直接红。
>
> 对应文档：[08 §5 质量门禁设计](../../docs/08-metrics-and-quality-gates.md)、[03 §5 性能框架](../../docs/03-test-frameworks.md)

---

## 1. 两个实现，两种用途

| 文件 | 用途 | 依赖 |
|---|---|---|
| `py_load_smoke.py` | **每次提交都跑**的性能冒烟：零外部依赖，起服务→打流量→判阈值 | Python 标准库 + httpx + uvicorn |
| `k6/load_test.js` | **发布前/夜间**的真压测：Go 二进制，单机吞吐远高于线程模型 | k6 v0.50+ |

两者共享同一套阈值口径（p95 / p99 / 错误率 / 吞吐），这样"冒烟拦得住"和"压测看得清"不会各说各话。

---

## 2. 运行

```bash
cd labs/04-perf

# 默认：20 并发 × 共 400 请求，自动起服务（随机端口）
python py_load_smoke.py

# 收紧门禁（演示"拦得住"）
python py_load_smoke.py --concurrency 50 --requests 1000 --p95 80 --max-error-rate 0.001

# k6 版本（需先安装 k6）
k6 run -e BASE_URL=http://127.0.0.1:8000 k6/load_test.js
```

实测输出（本机 Windows / Python 3.12，10 并发）：

```
请求数 300（并发 10）  耗时 1.10s
延迟 mean=14.4ms  p50=13.0ms  p95=17.0ms  p99=54.3ms
吞吐 272.3 req/s   错误率 0.00%

[PASS] p95    实际      17.03ms  要求 <= 200.0ms
[PASS] p99    实际      54.28ms  要求 <= 500.0ms
[PASS] 错误率    实际       0.00%  要求 <= 1.0%
[PASS] RPS    实际     272.31req/s  要求 >= 20.0req/s

门禁通过。
```

## 3. 门禁参数

| 参数 | 默认 | 含义 | 调法 |
|---|---|---|---|
| `--concurrency` | 20 | 并发客户端数 | 接近线上 P95 并发 |
| `--requests` | 400 | 总请求数 | 至少 200，否则分位数不可信 |
| `--p95` | 200ms | p95 上限 | 按 SLO 设，不按"当前实际值 +20%" |
| `--p99` | 500ms | p99 上限 | 长尾保护 |
| `--max-error-rate` | 1% | 错误率上限 | 核心链路应设 0.1% |
| `--min-rps` | 20 | 吞吐下限 | 防止"延迟很低但吞吐塌了" |

> **阈值怎么定**：先测出基线，再按业务 SLO 设阈值，**不要**按当前实测值加 20% 定——
> 那等于把"现状"固化成"目标"，系统劣化时门禁永远不响（[08 §3](../../docs/08-metrics-and-quality-gates.md)）。

---

## 4. 三条不可违反的压测纪律

1. **只压只读接口**。本实验压的是 `POST /api/quote`（试算，无副作用）。
   压 `POST /api/orders` 会制造真实数据，污染环境、拖垮库存，是事故级错误。
2. **独立账号与环境**。压测流量不能和真人共用配额、共用限流阈值。
3. **报告要能定位**：延迟分布 + 错误样例，而不是一个平均响应时间。均值会掩盖长尾。

## 6. 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 结果波动巨大 | 客户端先成为瓶颈（GIL + 线程） | 换 k6，或降并发看趋势而非绝对值 |
| p99 突然很高 | 首请求预热 / JIT / 连接池冷启动 | 先跑 20 次热身再统计 |
| 门禁天天红 | 阈值按理想值拍脑袋 | 用基线 × 1.5 起步，再逐季收紧 |
| 平均延迟好看 | 长尾被均值掩盖 | 必须看 p95 / p99，不看 mean |

## 7. 延伸练习

- 把 `--p95` 调到 5ms，观察门禁如何阻断（并理解"不合理的阈值 = 必然被绕过"）。
- 用 k6 的 `stages` 做阶梯加压，找出错误率开始抬升的拐点（容量上限）。
- 给 `py_load_smoke.py` 加"错误样例 Top5"输出，对比不同故障注入下的表现。
