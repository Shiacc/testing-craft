## 1. 这份文档解决什么问题

绝大多数团队在自动化测试上的失败，不是「不会写用例」，而是四类判断失误：

1. **方向错**：把该写接口测试的地方写成了 UI 测试，投入 3 倍成本换来 1/10 收益（→ [02](02-when-to-automate.md)、[07](07-engineering-and-ci.md)）
2. **工具错**：该用轻量框架的阶段上了重型平台，或该治理的阶段还在各自为战（→ [03](03-test-frameworks.md)、[04](04-test-platforms.md)、[05](05-selection-methodology.md)）
3. **治理缺位**：用例资产无人负责，一年后 40% 是失效用例与 flaky 用例，团队开始绕开测试（→ [08](08-metrics-and-quality-gates.md)、[09](09-organization-and-governance.md)）
4. **度量缺失**：无法回答「自动化到底带来了什么」，预算第一个被砍（→ [08](08-metrics-and-quality-gates.md)）

本文档按「**概念 → 决策 → 工具 → 落地 → 治理**」的因果链组织，而不是按工具各写一章。

## 4. 核心结论速查

如果把整份文档压缩成一页，是这 10 条：

1. **自动化的本质是把「判断是否通过」这个动作变成可复用资产**，只有判定标准确定、且会被重复执行时，自动化才有正收益。
2. **在能证明问题的最底层做断言**：单元 > 接口 > UI。企业实践中，接口层通常是投入产出比最高的主干。
3. **测试框架是代码库（进程内、随仓库走）；测试平台是服务（跨机器、独立运维）**。二者是分层关系，不是替代关系。
4. **框架解决「怎么表达测试」，平台解决「谁在什么环境跑了什么、结果如何、能否放行」**。
5. 平台底层仍要调用框架。**没有用例资产的平台只是空壳**——这是自建/采购平台失败的头号原因。
6. **先有框架 + CI + 度量，再评估平台**。单团队单仓库往往永远不需要平台。
7. 出现以下信号才该考虑平台：多团队共享资产、环境/设备矩阵、统一门禁与审计、非开发者要写用例、用例规模进入千级需要调度。
8. **flaky 用例比没有用例更伤**：它训练团队忽略红灯。把 flaky 率当作一级指标治理。
9. **门禁要少而硬**：3 条以内、失败即阻断、可解释；门禁越多，绕过文化越强。
10. **度量看结果（逃逸缺陷、MTTR、变更失败率），不看过程（用例数、覆盖率数字）**。

## 5. 文档约定

- **术语统一**：使用 [01 §5 术语表](01-concepts-and-terminology.md) 的定义；同义词只在首次出现时标注。
- **工具提及原则**：工具名用于举例，不代表推荐。选型结论走 [05](05-selection-methodology.md) 的加权评分流程，不允许「凭印象拍板」。
- **数据口径**：文中出现的比例、成本、耗时均为**业界经验区间**，用于建立数量级直觉，落地时须用自己团队的历史数据替换。
- **代码示例**：文档内只给最小片段；完整可运行版本在 [`labs/`](../labs/README.md)，避免文档与代码双维护导致漂移。
- **可执行性**：每条建议都应能被检验——「应该做 X」后面必须跟上「怎么判断做到了」。
