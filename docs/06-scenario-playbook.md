## 0. 手册用法：定位 → 取配方 → 6 个月路线

| 步骤 | 你要做的判断 | 输出 | 常见错误 |
|---|---|---|---|
| ① 定位 | 规模、发布频率、系统形态、合规要求，哪一项最约束你 | 一个主场景 + 至多一个副场景 | 按"行业"选（同业未必同病） |
| ② 取配方 | 分层配比是否与你的风险匹配 | 一张工具表 + ≤ 3 条门禁 | 全盘照抄，不裁剪 |
| ③ 执行 | 当前阶段只做最痛的那一件事 | 季度目标 + 可验收的完成标志 | 同时上 5 件事，全部半成品 |

两条纪律：**主场景决定配比，副场景只补充工具**（"微服务 + 强监管" = C 的配比 + F 的审计要求，不要两套配比各取一半）；**完成标志必须可测**（写"PR 构建 ≤ 10 分钟且全绿"，不写"提升测试能力"）。

场景速览：

| 场景 | 一句话识别 | 首要矛盾 |
|---|---|---|
| A 初创 | ≤ 10 人，需求周变 | 投入不能重，先保营收链路 |
| B 单体 | 20–80 人，单体，双周发布 | 回归靠人肉，需要主干自动化 |
| C 微服务 | 多团队，日均多次发布 | 契约与跨服务验证 |
| D 前端 / 移动 | 交互密集、多端 | UI 稳定性与设备矩阵 |
| E 数据 / AI | 结果不确定、依赖数据 | 判定标准与数据质量 |
| F 强监管 | 审计、留痕、不可篡改 | 证据链与可追溯 |
| G 遗留重构 | 换框架 / 换架构 | 用测试护住行为不变 |
| H 外包多方 | 多供应商交付 | 验收标准与责任边界 |

## 场景 A · 初创团队（≤ 10 人 / MVP 阶段）
**典型特征**　需求周级变化、一天多次发布；无专职 QA，开发自测；基础设施全部托管，没有运维人手。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 注册 → 付费链路断裂 | 直接损失收入 | L3 接口 + 1 条 L4 冒烟 |
| 计费、权限判断错误 | 退款与信任崩塌 | L1 单元（金额、权限矩阵） |
| 发布配错环境变量 / 密钥 | 全站不可用 | 部署后健康检查 + 冒烟 |

**分层配比建议**（**经验区间**，按用例条数计）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 55%–70% | 只测"错了会赔钱"的逻辑：金额、权限、状态机 |
| L3 接口 | 25%–35% | 覆盖全部对外 API 的正常路径 + 鉴权 |
| L4 E2E | 5%–10% | 3–5 条核心旅程，跑在预发环境；性能暂不做，用托管服务监控代替 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 单元 | pytest / Vitest（跟主语言） | 零运维，与现有代码同栈 |
| 接口 | httpx + pytest / Supertest | 不起浏览器，10 行能写完一条 |
| E2E | Playwright（只装 Chromium） | 不要一开始就上浏览器矩阵 |

**门禁与度量**　必过：单元 + 接口全绿即阻断合并；发布前：预发 5 条 E2E 通过。度量只看**每月逃逸缺陷数**，不看覆盖率。　**常见坑**　先搭 Selenium 矩阵（3 周搭完、3 个月废弃）｜追覆盖率数字，写出大量 `assert status == 200`｜没有预发环境，E2E 直接打生产。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1 月 | 建 CI，单元覆盖金额 / 权限 | 每次 PR 自动跑，≤ 5 分钟 |
| 2 | 第 2–3 月 | 接口覆盖全部对外 API | CI 稳定跑 2 周无人工干预 |
| 3 | 第 4–6 月 | 5 条 E2E + 预发环境 + flaky 记录 | 发布前自动冒烟，月度质量简报 |

## 场景 B · 20–80 人单体应用（中等发布频率）
**典型特征**　单体服务 + 关系库；双周或每周发布；1–3 名专职测试；回归靠 2–3 天手工点击。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 改 A 模块打挂 B 模块 | 回归漏测，线上事故 | L2 组件测试（handler + 真库） |
| 回归 3 天挤压发布窗口 | 发布延期或跳过回归 | L3 接口套件 + 分片并行 |
| 共用测试环境互相踩数据 | 用例随机失败，团队失去信任 | 环境隔离 + 数据自造自清 |

**分层配比建议**（**经验区间**）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 50%–65% | 领域逻辑、金额计算、状态流转 |
| L2 组件 | 15%–20% | 用 testcontainers 起真库，验 SQL 与事务 |
| L3 接口 | 20%–25% | 全接口正常 + 边界 + 鉴权 |
| L4 E2E | 5%–8% | 10–15 条核心业务流 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 单元 / 组件 | pytest + testcontainers / JUnit 5 + Spring Boot Test | 真库比 mock 更能抓住 SQL 与事务问题 |
| 接口 | httpx + pytest / REST Assured | 与单元同 runner，报告统一 |
| E2E | Playwright | 自动等待把 flaky 压到可治理水平 |

**门禁与度量**　PR：单元 + 接口全绿且 ≤ 10 分钟；发布：主干 E2E 冒烟通过。度量：回归耗时（目标从 3 天降到 2 小时，**经验区间**）、flaky 率 < 2%。　**常见坑**　所有回归搬 UI（成本翻 5 倍）｜共享测试库导致用例互相污染｜没有分片，套件跑 40 分钟后没人等结果。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1 月 | 建 CI，单元基线 | 每次 PR 自动跑，报告可查 |
| 2 | 第 2–3 月 | 接口覆盖核心域 + 引入 testcontainers | 接口套件 ≤ 8 分钟 |
| 3 | 第 4–6 月 | E2E 10 条 + 分片 + flaky 治理 | 回归总时长 ≤ 30 分钟，flaky < 2% |

## 场景 C · 微服务 / 多团队（日均多次发布）
**典型特征**　≥ 5 个服务、3 个以上团队、独立部署；发布日均多次；已有 K8s 与统一网关。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 接口字段变更打挂下游 | 跨团队线上故障 | L3 契约测试（消费方驱动） |
| 全链路环境不可用 | 所有 E2E 一起红，无人定位 | 契约 + 单服务接口测试为主 |
| 不知道改动影响哪些服务 | 回归范围靠猜 | 变更影响分析 + 服务级测试选择 |

**分层配比建议**（**经验区间**）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 55%–65% | 各服务本语言原生框架 |
| L2 组件 | 15%–20% | 服务内集成，真库 + stub 外部依赖 |
| L3 接口 + 契约 | 15%–20% | 接口验行为，契约验兼容，两者不可互替 |
| L4 E2E | 3%–5% | 只留跨服务的关键旅程 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 契约 | Pact（消费方驱动） | 唯一能在 provider 合并前拦住不兼容变更 |
| 接口 | httpx + pytest / REST Assured | 单服务可独立跑，不依赖全链路 |
| schema 校验 | Schemathesis | 顺手覆盖非法输入，接入成本极低 |

**门禁与度量**　provider 契约验证失败即阻断其发布；单服务接口 P95 阈值进 CI。度量：跨服务故障数、契约覆盖率（关键消费关系是否都有契约）。　**常见坑**　用全链路 E2E 代替契约（环境一挂全红）｜每个团队各建一套流水线，门禁无法统一｜契约写了但 provider 侧没人执行验证。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1–2 月 | 契约试点 2 个服务 | 一次真实不兼容变更被拦在合并前 |
| 2 | 第 3–4 月 | 全服务接入 + 门禁 | 关键消费关系 100% 有契约 |
| 3 | 第 5–6 月 | 变更影响分析 + 环境池 | 只跑受影响服务，全量时间降 40%+ |

## 场景 D · 前端或移动端为主的产品
**典型特征**　Web SPA / 小程序 / App；交互与视觉权重高；多端多版本并行；前端团队主导技术决策。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 视觉 / 布局回归 | 用户可见的错位与遮挡 | 视觉回归（快照对比） |
| 多端行为不一致 | 同一功能在某端不可用 | 组件测试 + 少量跨端 E2E |
| 弱网与设备碎片化 | 真机才复现的崩溃 | 设备云 + 弱网模拟 |

**分层配比建议**（**经验区间**，E2E 占比高于其他场景）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元（含组件） | 45%–60% | 组件测试是主力，测用户可见行为 |
| L2 集成 | 20%–25% | 页面级组合 + BFF 接口 |
| L3 接口 | 10%–15% | BFF / GraphQL 层 |
| L4 E2E + 视觉 | 10%–15% | 主流程 + 视觉基线 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 组件 | Vitest + Testing Library | 按用户行为断言，不测实现细节 |
| Web E2E | Playwright（含 `toHaveScreenshot`） | 一套工具同时解决 E2E 与视觉回归 |
| 移动 | Appium + 设备云 | 真机矩阵自建不划算 |
| 性能 | Lighthouse CI（首屏预算） | 前端最该守的指标，接入成本低 |

**门禁与度量**　视觉快照差异需人工确认后才可更新基线；LCP < 2.5 s 进 CI。度量：视觉回归噪音率（每周需人工确认的差异数）、崩溃率。　**常见坑**　组件测试断言 props 传递而非用户行为｜视觉回归容差设 0，天天红｜移动端只在模拟器验证，真机问题全漏。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1 月 | 组件测试基线 + 3 个页面视觉快照 | 快照进入版本控制 |
| 2 | 第 2–3 月 | Playwright 主流程 5 条 | 稳定跑 2 周无 flaky |
| 3 | 第 4–6 月 | 设备云 + 性能预算 | 真机回归可在 CI 触发，LCP 超阈值阻断 |

## 场景 E · 数据 / 算法 / AI 类产品
**典型特征**　输出是概率性的、没有唯一正确答案；强依赖数据集与模型版本；数据管道比服务更长。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 数据质量（缺失、漂移、训练集泄漏） | 效果静默下降，无人发现 | 数据质量检查（schema + 分布断言） |
| 模型效果回退 | 上线后指标变差 | 离线评估集 + 指标门禁 |
| 不可复现 | 同一实验跑出不同结果 | 数据与模型版本化 + 固定随机种子 |

**分层配比建议**（**经验区间**，与业务系统结构不同）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 数据变换 / 特征 | 40%–55% | 纯函数化后按单元测试对待 |
| 数据质量检查 | 20%–30% | 每张表、每个数据集入口都查 |
| 模型评估 | 15%–20% | 评估集上的指标，不是单条断言 |
| L3 / L4 | 5%–10% | 推理接口 + 端到端抽样 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 数据质量 | Great Expectations / pandera | 把"数据契约"变成可执行断言 |
| 版本与实验 | DVC + MLflow | 没有数据与模型版本就无法复现结论 |
| 不变量 | Hypothesis | 变换往返、归一化边界最易出错 |

**门禁与度量**　数据质量检查失败阻断训练；关键指标（召回 / F1）不得低于基线 −1%（**经验区间**，须按业务定）；推理 P95 延迟进门禁。　**常见坑**　只测"能跑通"不测"效果"｜评估集与训练集泄漏，指标虚高｜没有数据版本，结论不可复现。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1 月 | 数据质量检查 + 版本化 | 每次训练前自动跑检查 |
| 2 | 第 2–3 月 | 固定评估集 + 指标门禁 | 指标回退会被阻断 |
| 3 | 第 4–6 月 | 推理接口测试 + 漂移监控 | 线上分布偏移有告警，月度效果报告 |

## 场景 F · 金融 / 医疗等强监管行业
**典型特征**　合规与审计部门有否决权；要求证据可追溯、不可篡改；变更需审批；测试数据敏感。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 无法证明"测过" | 审计不通过，上线被否 | 执行记录归档（含人、时间、版本） |
| 越权访问 | 合规事故，最严重等级 | L3 鉴权 / 越权矩阵（占比高于其他场景） |
| 敏感数据流入测试环境 | 数据泄露，监管处罚 | 脱敏数据工厂 + 环境准入检查 |

**分层配比建议**（**经验区间**）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 50%–60% | 规则、限额、计息、状态机 |
| L3 接口（含鉴权矩阵） | 25%–30% | 角色 × 资源 × 操作的组合必须全覆盖 |
| L4 E2E | 5%–8% | 关键旅程 + 审批流；非功能（容量、故障演练）按需做且同样归档 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 框架 | pytest / JUnit 5（原生，不用平台私有 DSL） | 证据要能被独立复核 |
| 用例管理 | TestRail / 禅道等（**必须**） | 审计看的是需求—用例—结果的可追溯链 |
| 证据归档 | 对象存储 + 不可篡改策略（WORM / 只追加） | 日志可删 = 证据无效 |

**门禁与度量**　鉴权矩阵全绿为硬门禁（不可豁免）；执行记录与报告归档到不可篡改存储。度量：审计一次通过率、证据完整率（应有记录 vs 实有记录）。　**常见坑**　审计日志可被管理员删除｜用生产数据直接做测试｜把"通过率"当合规证据（缺执行人与时间戳）。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1–2 月 | 鉴权矩阵 + 证据归档设计 | 矩阵覆盖全部角色 × 资源组合 |
| 2 | 第 3–4 月 | 用例管理与审批流上线 | 任一用例可追到需求与执行记录 |
| 3 | 第 5–6 月 | 故障 / 容量演练 + 审计演练 | 模拟审计一次通过 |

## 场景 G · 遗留系统重构 / 换框架迁移
**典型特征**　存量系统缺测试或测试不可信；要换框架、拆服务或换语言；对外行为必须保持不变。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 重构引入行为差异 | 上线后功能悄悄变了 | 特征测试（characterization）锁住旧行为 |
| 新旧并行期数据不一致 | 双写差异，对账不平 | 流量镜像 + 响应差异对比 |
| 测试跟着旧实现写 | 迁移后套件全部失效 | 断言对外契约，不断言内部调用 |

**分层配比建议**（**经验区间**，接口层占比最高）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 30%–40% | 只为"即将改动的逻辑"补，不追求全覆盖 |
| L3 特征 / 接口 | 40%–50% | 记录旧系统真实响应作为基线 |
| L4 对照 E2E | 5%–10% | 新旧系统跑同一旅程，比对结果；性能基线等迁移完成后重建 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 特征测试 | ApprovalTests / 快照断言 | 把"当前行为"固化成可 diff 的基线 |
| 流量 | 流量镜像 + VCR 式录制回放 | 真实请求分布是唯一可信的输入集 |
| 差异对比 | 自研 diff 脚本（新旧响应逐字段比） | 迁移期最有效的单一工具 |

**门禁与度量**　关键接口新旧响应差异率必须为 0；重构分支每 PR 必跑特征套件。度量：差异率、特征测试覆盖率（按接口数）。　**常见坑**　先重构再补测试（顺序反了，等于无保护手术）｜用"理想用例"覆盖，漏掉历史怪癖与兼容分支｜无流量镜像，输入集靠想象。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1–2 月 | 特征测试覆盖核心域 | 核心接口有可 diff 的响应基线 |
| 2 | 第 3–4 月 | 流量镜像 + 差异对比 + 契约 | 能跑出真实请求的差异报告 |
| 3 | 第 5–6 月 | 分批迁移 | 每批迁移差异率为 0，下线检查单齐备 |

## 场景 H · 外包与多供应商协作
**典型特征**　多方交付同一系统；验收标准写在合同里；资产归属与交接存在风险；供应商工具链各异。

**主要质量风险**

| 风险 | 后果 | 该在哪层挡 |
|---|---|---|
| 验收标准模糊 | 验收扯皮，工期失控 | 甲方主导的可执行验收套件 |
| 资产交付不完整 | 换供应商时无法接手 | 交付清单 + 甲方 CI 可跑通 |
| 责任边界不清 | 缺陷归属争议 | 分层责任表（单元供应商、验收甲方） |

**分层配比建议**（**经验区间**，由甲方定义并写入合同）

| 层 | 占比 | 说明 |
|---|---|---|
| L1 单元 | 40%–55% | 供应商自测，甲方抽检覆盖率与断言质量 |
| L3 接口 | 25%–35% | 甲方主导，作为验收硬指标 |
| L4 E2E | 5%–10% | 甲方验收旅程，不交给供应商独占 |
| L5 性能 | 按合同 | 明确并发口径与验收环境 |

**工具组合推荐**

| 层 | 推荐 | 理由 |
|---|---|---|
| 验收套件 | 甲方自有仓库 + 标准框架（pytest / Playwright） | 资产必须留在甲方手里 |
| 报告 | JUnit XML + Allure（固定格式） | 换供应商不改流程 |
| 资产清单 | 脚本、数据构造逻辑、环境脚本、文档 | 只交脚本不交数据构造 = 交接失败 |

**门禁与度量**　验收套件通过率 100% 才触发付款 / 交付节点；资产清单齐全为验收前置。度量：验收一次通过率、缺陷归属争议数、交接耗时。　**常见坑**　验收标准写"满足需求"（不可检验）｜供应商用自己平台跑，结果不可复现｜交接只给脚本，不给测试数据与账号体系。

**6 个月落地路线**

| 阶段 | 时间 | 目标 | 完成标志 |
|---|---|---|---|
| 1 | 第 1 月 | 可检验验收标准 + 资产清单 | 每条标准都对应一条用例 |
| 2 | 第 2–3 月 | 甲方验收套件 | 覆盖全部验收条款 |
| 3 | 第 4–6 月 | 纳入甲方 CI + 交接演练 | 供应商提交即自动验收，演练一次通过 |

## 跨场景的通用起步顺序

无论哪个场景，前 90 天的顺序基本一致——这与技术栈无关，只与"人会不会用"有关：

```
第 1 步  把"能跑"变成"每次提交都跑"        → CI 里有一条稳定流水线
第 2 步  在最便宜的一层写第一条有效断言    → 单元或接口，10 条以内
第 3 步  让失败能被人看见                  → 报告聚合 + 通知
第 4 步  加第一条硬门禁（只加一条）        → 阻断合并，不允许"先合后修"
第 5 步  治 flaky                          → 不治则前面全部作废
第 6 步  再谈平台与矩阵                    → 对照 04 §7 前置条件
```

反序的典型后果：先买平台 / 设备云 → 空壳平台，许可费照付；先写 200 条 E2E → 60% flaky，团队集体忽略红灯；先追覆盖率 → 断言极弱，变异测试一跑即穿；先做性能压测 → 业务还不稳定，压出的数字无意义。

**如果只能做一件事，做那条"每次提交都跑、失败即阻断"的流水线。** 它比任何框架和平台都更能改变团队行为。
