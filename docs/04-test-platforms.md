# 04 · 测试平台全景

> **适用读者**：测试架构师、QA 负责人、研发效能 / 平台团队　|　**前置阅读**：[01 概念与术语](01-concepts-and-terminology.md)（尤其 §4、§5）、[03 测试框架全景](03-test-frameworks.md)　|　**配套实验**：[labs/](../labs/README.md)（含轻量测试平台原型）
>
> 本文只讨论**测试平台**——独立部署的服务系统。文中成本、周期、比例为**业界经验区间**，用于建立数量级直觉；采购与自建预算必须以自身询价与人力成本重算。

## 1. 平台的真实价值边界

结论先行：**平台买的是"组织协同与治理"，不买"用例质量"。** 用例写得烂，上平台只是让烂用例跑得更快、更显眼、更贵。

| 你遇到的问题 | 平台能否解决 | 说明 |
|---|---|---|
| 用例散落在各人电脑，人一走全丢 | ✅ 能 | 资产管理是平台的原生能力 |
| 不知道昨晚谁跑了什么、结果如何 | ✅ 能 | 调度 + 结果聚合 + 趋势 |
| 需要真机 / 多浏览器矩阵 | ✅ 能（或只能靠设备云） | 自建设备池成本极高 |
| 发布前想统一卡一道门禁 | ✅ 能 | 门禁引擎 + 与 CI/CD 联动 |
| 审计要求"谁在何时改了哪条用例" | ✅ 能 | 权限与审计留痕 |
| 用例断言太弱、覆盖错了地方 | ❌ 不能 | 方法论问题，见 [02](02-when-to-automate.md)、[03](03-test-frameworks.md) |
| flaky 率高 | ❌ 不能 | 平台只能暴露它，治理要靠 [07](07-engineering-and-ci.md) |
| 团队不想写测试 | ❌ 不能 | 组织问题，见 [09](09-organization-and-governance.md) |

判断表：

| 情形 | 判断 | 依据 |
|---|---|---|
| 单团队、单仓库、用例 < 500、CI 已稳定 | **平台是负担** | 框架 + CI 已覆盖 90% 需求，多一套系统多一份值班 |
| 2–3 个团队共享用例，靠口头同步 | 拼装方案足够 | 见 §6 |
| ≥ 3 团队、有设备矩阵、有合规审计 | **平台是解药** | 协同成本已超过平台运维成本 |
| 非开发者（业务 / 产品）要参与用例 | 平台（或低代码层）是解药 | 无法要求业务方提 PR |
| 把平台当"提升测试质量"的项目立项 | 立项即失败 | 目标错，验收无从定义 |

一条反直觉结论：**平台的上线成本远低于它的运营成本。** 上线 3 个月能完成，运营需要 3 年持续投入（**经验区间**：1 名全职平台负责人 + 0.5 名运维）。

## 2. 能力模型与最小可用平台

[01 §4.2](01-concepts-and-terminology.md) 给出九大能力域。把它们全部平台化是浪费——**平台化收益并不均等**：

| 能力域 | 平台化收益 | 单团队是否必需 | 说明 |
|---|---|---|---|
| 资产管理 | 高 | 否（Git 已足够） | 平台价值在"跨项目复用 + 非开发者可见" |
| 调度执行 | 高 | 否（CI 已足够） | 平台价值在"按需触发 + 排队 + 配额" |
| 环境与设备 | 极高 | 视需求 | 唯一"自建几乎不划算"的能力域 |
| 结果与报告 | 高 | 部分（Allure 可替代） | 平台价值在"跨项目趋势" |
| 质量门禁 | 高 | 部分（CI 可做） | 平台价值在"统一策略 + 豁免留痕" |
| 权限与审计 | 极高（强监管） | 否 | 合规行业里它常是立项主因 |
| 流程集成 | 中 | 否 | 需求—用例—缺陷追溯，收益随组织复杂度上升 |
| 低代码 | 中高 | 否 | 有业务方参与时变为必须 |
| 数据管理 | 中 | 否 | 最容易被低估，也最容易做成半成品 |

### 2.1 最小可用平台（MVP）：4 项必备

任何平台项目，先只做这 4 项。**做不出来，说明组织还没准备好（见 §7）。**

| # | 能力 | 为什么不可删 | 最小实现（**经验区间**） |
|---|---|---|---|
| 1 | **统一执行入口** | 没有它，平台只是一个文档库 | 一个 API + 队列，能按"用例集 × 环境"拉起一次执行 |
| 2 | **结果聚合与历史** | 没有趋势就无法判断"变好还是变坏" | 每次执行落库：用例、状态、耗时、日志链接；提供按周趋势 |
| 3 | **环境配置管理** | 环境靠人脑记忆是 flaky 的第一大来源 | 环境名 → baseURL / 凭据 / 数据集的注册表，凭据走密钥管理 |
| 4 | **门禁与通知** | 平台不阻断，就没人看报告 | 通过率 / 失败数阈值 + webhook 回写 CI，失败阻断合并 |

明确**不在 MVP** 内：低代码编排、AI 生成用例、跨系统需求追溯、自定义报表设计器。这些是第二年的事，提前做会拖垮第一期。

### 2.2 职责分界：同一个动作该由谁负责

平台项目最常见的返工，是把框架或 CI 已经做好的事在平台里重做一遍。按下表划清边界：

| 动作 | 归属 | 理由 |
|---|---|---|
| 用例的编写、断言、替身 | **框架** | 需要代码能力与本地调试体验 |
| 用例的版本与评审 | **Git** | 已是最好的版本管理与评审工具 |
| 每次提交跑哪些用例 | **CI** | 与构建同源，改一处即生效 |
| 分片与并发 | CI（少量）→ 平台（大规模） | 超过 20 个执行单元后需要配额与排队 |
| 环境与凭据注册 | **平台** | 需要跨项目共享与权限控制 |
| 结果的历史趋势 | **平台** | CI 只保留有限期制品 |
| 门禁阈值与豁免 | **平台**（策略）/ CI（执行） | 策略要统一，执行要就近 |
| 设备与浏览器矩阵 | **平台或设备云** | 资源池化才有意义 |

一句话总结：**平台负责"跨"字——跨项目、跨环境、跨团队、跨时间；不跨的东西留给框架和 Git。**

## 3. 五类平台详解

### 3.1 用例管理型（TestRail、Zephyr、禅道 / PingCode）

- **做什么**：用例目录、版本、执行计划、与需求/缺陷关联、手工与自动化结果登记。
- **不做什么**：**不执行**。结果要靠 CI 或框架回写 API。
- **价值点**：让"测试覆盖了什么"对非技术角色可见，是验收与审计的证据链。
- **风险**：很容易变成"只登记不执行"的台账，半年后与真实状态脱节。

### 3.2 执行 / 全栈型（Katalon、MeterSphere、自研）

- **做什么**：管理 + 编排 + 执行 + 报告一体，通常内嵌自研框架或封装开源框架。
- **价值点**：开箱即用，非开发者也能拼流程；省掉大量集成工作。
- **风险**：**框架不可脱离平台使用**（锁定）；复杂断言与调试能力弱于原生框架；版本升级常破坏存量脚本。

### 3.3 设备与浏览器云（BrowserStack、Sauce Labs、云真机）

- **做什么**：真机 / 浏览器矩阵、并行会话、录屏与日志。
- **价值点**：唯一"自建明显不划算"的能力；解决 iOS 真机、老版本浏览器、弱网模拟。
- **风险**：按并行数计费，成本随 CI 频率线性上升；网络延迟会恶化 UI 用例稳定性。

### 3.4 流水线与报告层（Jenkins、GitLab CI、Allure）

- **做什么**：触发、编排、分片、归档、报告可视化。
- **明确结论：它们不是完整测试平台。** 缺资产管理、环境池、门禁策略、审计留痕。
- **价值点**：作为平台的执行后端与报告前端，几乎不可替代；也是拼装方案的主力。

### 3.5 可观测 / 合成监控（Datadog Synthetics、Grafana Synthetic Monitoring）

- **做什么**：线上定时拨测核心链路、断言业务结果、告警。
- **价值点**：把 E2E 能力复用到生产，是最接近真实用户的信号。
- **风险**：与测试环境用例资产双轨维护；线上拨测会产生真实数据与费用，必须用影子账号 / 沙箱商户。

### 3.6 五类平台横评

| 类型 | 代表 | 部署形态 | 是否执行 | 设备矩阵 | 扩展性 | 锁定风险 | 成本区间（**经验区间**） | 适用规模 |
|---|---|---|---|---|---|---|---|---|
| 用例管理型 | TestRail、Zephyr、禅道 / PingCode | SaaS / 私有部署 | ❌ | ❌ | 中（API 回写） | 低（数据可导出） | 200–600 元/人/年 | 10 人以上，需追溯 |
| 执行全栈型 | Katalon、MeterSphere、自研 | 私有部署为主 | ✅ | 中（依赖设备云） | 中低（插件受限） | **高** | 3,000–8,000 元/人/年 或 自研人力 | 50 人以上多团队 |
| 设备与浏览器云 | BrowserStack、Sauce Labs、云真机 | SaaS | ✅（只执行） | **极高** | 低（API 固定） | 中（脚本可迁） | 1,000–3,000 元/并发/月 | 有移动端 / 多浏览器需求 |
| 流水线与报告 | Jenkins、GitLab CI、Allure | 私有 / SaaS | ✅（只编排） | ❌ | **极高** | 低（开源） | 0–500 元/人/年（另计人力） | 所有规模 |
| 可观测 / 合成 | Datadog Synthetics、Grafana | SaaS / 私有 | ✅（线上） | 中 | 中 | 中 | 按拨测次数计费，数百–数千元/月 | 已上线且有 SLO |

> 成本列只用于比较量级。同一产品在不同席位 / 并发 / 年限下报价差异可达 3 倍，必须以询价书为准（模板见 [11 §平台 RFP](11-templates-and-checklists.md)）。

## 4. 自建 vs 采购 vs 拼装

### 4.1 三条路线对比

| 维度 | 自建 | 采购（商用） | 拼装（开源组合） |
|---|---|---|---|
| 首年投入 | 高：3–5 人 × 4–8 个月 | 中：许可费 + 1–2 人集成 | 低：0.5–1 人 × 2–3 个月 |
| 3 年 TCO | 最高（人力是持续项） | 中高（随席位增长） | 最低 |
| 上线周期 | 6–12 个月 | 1–3 个月 | 2–6 周 |
| 贴合度 | 最高（按自己流程长） | 中（要改流程适配产品） | 中（靠 CI 编排补） |
| 扩展性 | 取决于团队 | 受产品边界限制 | 高（组件可替换） |
| 锁定风险 | 无（但人才锁定） | 高 | 低 |
| 典型失败模式 | 烂尾、无人运营 | 空壳、续费绑架 | 拼不起来、维护碎片化 |

### 4.2 成本算例（自建，**经验区间**）

假设：3 人团队、6 个月建成 MVP、人力成本 3 万元/人月、上线后 1.5 人维护。

| 阶段 | 计算 | 金额 |
|---|---|---|
| 建设期 | 3 人 × 6 月 × 3 万 | 54 万 |
| 第 1–3 年运维 | 1.5 人 × 36 月 × 3 万 | 162 万 |
| 基础设施（服务器 / 存储 / 设备） | 3 年 | 15–30 万 |
| **3 年合计** | — | **约 230–250 万** |

三条对照（同口径，**经验区间**）：

| 路线 | 3 年成本估算 | 计算口径 |
|---|---|---|
| 自建 | 230–250 万 | 见上表 |
| 采购全栈型 | 约 150 万 | 100 名工程席 × 5,000 元/人/年 × 3 年 |
| 拼装 | 约 60 万 | 0.5 人 × 36 月 × 3 万 + 一次性集成 6 万 |

结论：**只有当需要的能力超出商用产品边界（通常是"深度集成自有研发流程"或"强监管审计"）时，自建才在数学上成立。** 否则自建是拿最贵的资源（工程师）去做最不差异化的事。

### 4.3 决策建议

| 你的处境 | 建议路线 | 备注 |
|---|---|---|
| ≤ 3 团队、无合规要求 | **拼装**：CI + Allure + 轻量用例管理 | 先跑 6 个月再评估 |
| 有设备矩阵需求 | 拼装 + **采购设备云** | 设备层不要自建 |
| 有审计 / 合规要求（金融、医疗） | **采购**具备审计能力的方案，或私有部署全栈型 | 自建审计的成本极高 |
| 流程高度特殊（如硬件在环、专用协议） | **自建**，范围严格限定在差异化部分 | 通用能力仍然买 |
| 已有平台但用不起来 | 先做运营，不要换平台 | 见 §8「无人运营」 |

## 5. 平台参考架构

```
┌──────────────────────────────────────────────────────────┐
│  Web UI / OpenAPI        选用例 · 选环境 · 触发 · 看报告     │
└───────────────┬──────────────────────────────────────────┘
                │ 提交执行请求（用例集 × 环境 × 参数）
┌───────────────▼──────────┐
│  任务队列                 │  优先级 · 去重 · 重试 · 超时
└───────────────┬──────────┘
┌───────────────▼──────────┐        ┌──────────────────────┐
│  调度器（Scheduler）      │◄──────►│  环境池               │
│  分片 · 并发配额 · 依赖    │        │  注册 · 隔离 · 回收    │
└───────────────┬──────────┘        └──────────────────────┘
        ┌───────┼────────┬─────────┐
┌───────▼──┐ ┌──▼───────┐ ┌▼────────┐
│ agent 1  │ │ agent 2  │ │ agent N │   执行机池（pytest / playwright / k6）
└───────┬──┘ └──┬───────┘ └┬────────┘
        └───────┼──────────┘
┌───────────────▼──────────┐        ┌──────────────────────┐
│  结果存储                 │───────►│  报告与趋势           │
│  执行 · 用例 · 日志 · 制品 │        │  聚合 · 对比 · 归因    │
└───────────────┬──────────┘        └──────────┬───────────┘
        ┌───────▼──────────┐        ┌──────────▼───────────┐
        │  门禁引擎         │        │  权限与审计           │
        │  阈值 · 阻断 · 豁免│        │  角色 · 留痕 · 导出    │
        └──────────────────┘        └──────────────────────┘
```

| 组件 | 职责 | 常见技术选型 | 常见坑 |
|---|---|---|---|
| 任务队列 | 削峰、重试、优先级 | Redis Stream / RabbitMQ / Kafka | 用数据库轮询当队列，高并发下锁表 |
| 调度器 | 分片、并发配额、依赖编排 | 自研 + K8s Job / Celery | 分片按用例数均分而非按耗时，长尾拖死整体 |
| 执行机池 | 真正跑用例 | K8s Pod / 虚机 / Docker | 镜像不固定版本，同一用例昨天过今天挂 |
| 环境池 | 环境注册、隔离、回收 | K8s namespace / 独立租户 | 环境不回收，跑一周后数据污染 |
| 结果存储 | 执行与用例事实表 | PostgreSQL + 对象存储 | 日志塞进关系库，三个月后查询超时 |
| 报告与趋势 | 聚合、对比、归因 | Allure + 自研看板 / Grafana | 只存最后一次结果，无法做趋势 |
| 门禁引擎 | 阈值判定、阻断、豁免 | 自研 + CI webhook | 阈值可被随意修改，等于没有门禁 |
| 权限与审计 | RBAC、操作留痕 | 对接企业 SSO | 审计日志可被管理员删除，合规场景直接失效 |

部署侧三条经验：

1. **执行机必须镜像化且版本钉死**，这是"环境不一致"的唯一解。
2. 日志 / 截图 / trace 走对象存储，数据库只存索引与元数据。
3. 门禁引擎的权限要与平台日常操作分离，改阈值需独立审批（见 [09](09-organization-and-governance.md)）。

### 5.1 容量估算算例

平台最常见的技术债是"执行机不够 → 排队 → 大家不用"。用下面的方式倒推，而不是先买机器：

| 输入 | 取值（示例） | 说明 |
|---|---|---|
| 用例总数 | 3,000 条 | 全量回归规模 |
| 平均单例耗时 | 8 秒 | 接口层为主，E2E 拉高均值 |
| 单次全量串行耗时 | 3,000 × 8 s ≈ 6.7 小时 | 无法接受 |
| 期望完成时间 | 30 分钟 | 与发布节奏匹配 |
| 所需并行度 | 6.7 h ÷ 0.5 h ≈ 14 路 | 向上取整并留 30% 余量 → 18 路 |
| 单机可承载并发 | 4 路（经验区间） | 受 CPU 与浏览器内存限制 |
| 执行机数量 | 18 ÷ 4 ≈ 5 台（另加 1 台冗余） | 结论：6 台 |

两个必须写进设计的约束：

- **按耗时切分，不按条数切分**。否则慢用例集中在最后一个分片，整体时间由最慢分片决定。
- **队列要有优先级**。PR 触发的增量测试必须能插队到夜间全量之前，否则开发等红灯就绕开测试。

## 6. 拼装方案：能否替代平台

对照组：`GitLab CI / Gitee Go + Allure + TestRail`。按 [01 §4.2](01-concepts-and-terminology.md) 九大能力域逐项打分（● 覆盖 / ◐ 部分 / ○ 缺失）。

| 能力域 | 拼装方案 | 说明 | 商用全栈平台 | 差距是否致命 |
|---|---|---|---|---|
| 资产管理 | ◐ | TestRail 管用例、脚本在 Git，存在双份真相 | ● | 中：约定"以 Git 为准"可控 |
| 调度执行 | ◐ | CI 能定时 / 触发 / 分片，但无按需排队与配额 | ● | 低：多数团队够用 |
| 环境与设备 | ○ | 无环境池、无设备矩阵 | ● | **高**：有矩阵需求即不可替代 |
| 结果与报告 | ● | Allure + CI 制品，趋势靠自建脚本 | ● | 低 |
| 质量门禁 | ◐ | CI 能阻断，但策略散落在各仓库 yml | ● | 中：策略不统一 |
| 权限与审计 | ○ | Git 权限 ≠ 测试操作审计 | ● | **高**：合规场景致命 |
| 流程集成 | ◐ | TestRail 可连 Jira，但执行结果回写需自研 | ● | 中 |
| 低代码 | ○ | 无 | ◐ | 高（若有业务方参与） |
| 数据管理 | ○ | 无 | ◐ | 中：靠测试代码自造数据 |

**结论：拼装方案能覆盖 3.5 / 9，适合"≤ 3 团队、无设备矩阵、无合规审计"的阶段，是 6–18 个月的合理过渡。** 一旦出现"环境池"或"审计"需求，拼装的边际成本会陡升——那时再上平台，而不是现在硬上。

三问判断（任一为"是"就不该停在拼装）：

1. 是否需要给非 Git 用户（业务、审计、外部供应商）看用例与结果？
2. 是否需要统一的设备 / 浏览器矩阵？
3. 是否需要"谁改了门禁阈值"可追溯？

## 7. 平台引入的 6 条硬前置

不满足就不该上。**这 6 条是立项门槛，不是努力方向。**

| # | 前置条件 | 可检验判据 | 不满足的后果 |
|---|---|---|---|
| 1 | 已有稳定用例资产 | ≥ 300 条自动化用例，且月维护投入已成型 | 空壳平台：有界面没内容 |
| 2 | CI 已能稳定跑测试 | 主干构建成功率 ≥ 90%，有 JUnit XML 聚合 | 平台接的是不稳定流水线，问题被放大 |
| 3 | 有明确的多团队 / 矩阵 / 审计需求 | 能写出 3 条"没有平台就做不到"的具体场景 | 上线后无人使用 |
| 4 | 有确定的平台负责人 | 具名到人，≥ 0.5 FTE，写入考核 | 上线即巅峰，半年后荒废 |
| 5 | 有覆盖 3 年的预算（含运维） | 不只是首年许可费 | 第二年断供，迁移成本翻倍 |
| 6 | 有可退出的迁移方案 | 用例与结果能导出为通用格式并验证过一次 | 被厂商锁定，议价权归零 |

判据的使用方式：立项评审时逐条打勾，**打不出勾的条目要写成风险条目与缓解措施，而不是"我们努力做到"**。

### 7.1 不满足前置时该做什么

上不了平台不等于什么都做不了。按下表选择替代动作，通常 1–2 个季度就能补齐前置：

| 缺哪条 | 先做这个 | 大致周期（**经验区间**） |
|---|---|---|
| 用例资产不足 | 按 [06 场景手册](06-scenario-playbook.md) 补接口层用例 | 2–3 个月到 300 条 |
| CI 不稳定 | 先治 flaky 与构建超时（[07](07-engineering-and-ci.md)） | 1–2 个月 |
| 需求不明确 | 写 3 条"没有平台就做不到"的场景，验证是否真实 | 1–2 周 |
| 没有负责人 | 先指定 0.5 FTE，用拼装方案过渡 | 立即 |
| 预算不足 3 年 | 缩短合同期 + 强化导出条款，或先拼装 | 谈判期 |
| 无迁移方案 | 在 PoC 阶段强制要求导出演练 | PoC 内完成 |

## 8. 五种典型失败模式

| 失败模式 | 症状 | 根因 | 预防 |
|---|---|---|---|
| **空壳平台** | 上线 3 个月，用例数 < 50，无人登录 | 先买平台后想用例 | 先满足 §7 第 1、2 条 |
| **执行机地狱** | "本地能过、平台上挂"，同一用例结果随机 | 镜像不固定、环境不隔离、时钟与时区不一致 | 镜像版本钉死 + 环境即代码（[07](07-engineering-and-ci.md)） |
| **门禁失效（红灯文化）** | 红灯长期挂着，团队学会忽略 | 门禁太多、太软、可随手改 | 门禁 ≤ 3 条、失败即阻断、改阈值需审批（[08](08-metrics-and-quality-gates.md)） |
| **锁定** | 想换工具，发现用例无法导出 | 用例绑在平台私有 DSL 上 | 选型时做"导出 + 离线跑通"验证 |
| **无人运营（上线即巅峰）** | 首月使用率 80%，第 6 个月 10% | 无 owner、无培训、无迭代 | 0.5–1 FTE owner + 季度运营指标（[09](09-organization-and-governance.md)） |

一条经验：**这五种失败里，只有"锁定"是选型问题，其余四种都是运营问题。** 所以平台项目的成败主要发生在上线之后。
