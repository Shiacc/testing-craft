# 02 · 自动化决策模型

> **适用读者**：技术负责人、QA 负责人、架构师　|　**前置阅读**：[01 概念与术语](01-concepts-and-terminology.md)　|　**配套实验**：[labs/01-unit-pytest](../labs/01-unit-pytest/README.md)
>
> 本文回答一个问题：**这段验证，该不该自动化？** 不给口号，给可计算的流程。

---

## 1. 一个公式与三个变量

```
净收益 = 执行次数 × 单次人工成本 × 人工漏检率 − (编写成本 + 维护成本 + 基础设施成本)
```

三个变量决定一切：

| 变量 | 什么在驱动它 | 什么时候会失效 |
|---|---|---|
| **执行次数** | 发布频率、回归频率、上线环境数 | 一年跑 3 次的项目，自动化几乎必然亏本 |
| **判定确定性** | 需求是否可量化、结果是否可比对 | 审美、体验、"感觉好不好"，机器判不了 |
| **变更频率** | 需求稳定性、UI 改动频率、外部依赖变化 | UI 每周大改，脚本维护成本可能超过人工测试 |

> **关键认知**：维护成本通常是编写成本的 **2–5 倍**（业界经验区间）。选型与方案评审时只算编写成本，是 90% 的自动化项目亏损的真实原因。

## 2. ROI 算例：三种典型场景

假设一轮人工回归 8 人时，单次人力成本 ¥300/人时。人工漏检率按 10% 计（业界经验区间，用于建立数量级直觉）。

### 场景 A：高频回归（每天 3 次发布）

| 项 | 数值 |
|---|---|
| 年执行次数 | 3 × 250 = 750 次 |
| 人工成本/次 | 8 × 300 = ¥2,400 |
| 年人工总成本 | ¥1,800,000 |
| 自动化编写 | 120 人时 ≈ ¥36,000 |
| 年维护（按编写的 3 倍分摊到 3 年） | ≈ ¥36,000/年 |
| 基础设施（执行机 + 平台分摊） | ≈ ¥24,000/年 |
| **年净收益** | **≈ ¥1,704,000** |
| 回收期 | **约 1 周** |

**结论：必须自动化，且越早越好。** 这类场景下，不上自动化的代价是明显的资金浪费。

### 场景 B：中频回归（每周一次）

| 项 | 数值 |
|---|---|
| 年执行次数 | 50 次 |
| 年人工总成本 | ¥120,000 |
| 编写 + 首年维护 | ¥36,000 + ¥36,000 = ¥72,000 |
| 基础设施 | ¥24,000 |
| **年净收益** | **≈ ¥24,000** |
| 回收期 | **约 8 个月** |

**结论：值得做，但只值得做"主干"**——核心链路 + 易错分支。不要铺开写全量，边际用例的 ROI 会变成负数。

### 场景 C：低频（每季度一次大版本）

| 项 | 数值 |
|---|---|
| 年执行次数 | 4 次 |
| 年人工总成本 | ¥9,600 |
| 编写 + 首年维护 | ¥72,000 |
| **年净收益** | **≈ −¥62,400** |

**结论：不应该做全量自动化。** 只做**极少数上线前置检查**（冒烟，10–15 条关键路径），其余靠结构化手工检查清单。若这个系统未来会提频，则先修发布流程，再谈自动化。

> 算例的用法不是照抄数字，而是**用自己团队的人时成本、发布频率替换后重算一遍**。一个 15 分钟的表格推演，能省掉半年的错误投入。

## 3. 强信号：出现即应自动化

| # | 信号 | 判断依据 | 优先做什么 |
|---|---|---|---|
| S1 | 发布频率 ≥ 每周一次 | 人工回归成为发版瓶颈 | 核心链路接口回归集 |
| S2 | 判定标准可完全量化 | 金额、状态、字段、条数、错误码 | 单元 + 接口测试 |
| S3 | 出错代价高 | 资金、权限、数据一致性、合规 | 该模块的边界与异常分支全覆盖 |
| S4 | 组合矩阵爆炸 | 浏览器 × 设备 × OS × 语言 | 分层 + 设备云，不追求全矩阵 |
| S5 | 需要长时间/高并发观察 | 性能、稳定性、内存泄漏 | 性能脚本 + 阈值门禁 |
| S6 | 需要可追溯证据 | 审计、验收、发版准入 | 报告归档 + 门禁留痕 |
| S7 | 即将重构或换技术栈 | 需要锁定当前行为 | 先写特性测试（characterization test） |
| S8 | 线上需要持续探活 | 用户先发现问题的成本高 | 合成监控 / 拨测 |
| S9 | 重复的手工数据准备 | 每次都要造 50 条数据 | 数据工厂 + 自动化 |

---

## 4. 弱信号：不要勉强自动化

| 场景 | 为什么不该（或不该优先） | 替代做法 |
|---|---|---|
| 需求/UI 剧烈变动期 | 脚本写完即废，维护成本倒挂 | 只自动化工稳定内核（计算、接口），UI 手工 + 少量冒烟 |
| 一次性活动 | 执行次数 = 1，ROI 必为负 | 手工 + 检查清单 |
| 探索性测试 | 价值来自人的临场判断与联想 | 保留为专职活动，用自动化腾出的时间做更多探索 |
| 可用性 / 审美 / 文案 | 无确定 oracle，机器无法判定 | 用户测试、专家评审、A/B |
| 环境极难构造 | 第三方不可控、真实硬件 | 边界处做替身，仅保留少量真实环境验证 |
| 极低频低风险路径 | 年执行 < 5 次 | 手工清单 + 上线后监控 |
| 为"自动化率"指标而做的用例 | 目标错位，产出无价值用例 | 见 [08 §3 不要用的指标](08-metrics-and-quality-gates.md) |

> **判断口诀**：**"如果这段验证一年只做三次，或者我说不清什么算对，就别自动化。"**

## 6. 分层优先级：先解决"证明层级"

同一个风险，往往能在多层被证明，**选最底层**：

| 风险 | 可在 L1 证明 | 可在 L3 证明 | 只能 L4 证明 | 建议层级 |
|---|---|---|---|---|
| 优惠金额算错 | ✅ | ✅ | ✅ | **L1**（最快最稳） |
| 非法参数返回码错误 | 部分 | ✅ | ✅ | **L3** |
| 服务间字段改名导致下游崩 | ❌ | ✅ 契约 | ✅ | **L3 契约** |
| 登录后会话丢失 | ❌ | 部分 | ✅ | **L4**（少量） |
| 页面表单无法提交 | ❌ | ❌ | ✅ | **L4** |
| 万级并发超时 | ❌ | ❌ | ❌ | **L5 性能** |

**经验配比**（接口型业务系统，业界经验区间）：L1 50%–70%、L2 15%–25%、L3 10%–20%、L4 5%–10%。
比例不是目标，而是**体检指标**：L4 占比超过 20% 通常意味着 L3 存在空洞，成本结构正在恶化。

## 7. 自动化的四类对象（分别有不同的设计要点）

| 类型 | 目的 | 设计要点 | 典型产出 |
|---|---|---|---|
| **回归保护** | 改动不破坏既有行为 | 覆盖业务关键路径 + 历史缺陷点（每个线上 bug 一条用例） | 接口回归集、单元测试 |
| **契约与数据** | 服务间兼容、数据正确 | 消费方定义契约；数据不变量断言 | 契约测试、数据校验脚本 |
| **性能与容量** | 知道系统在什么条件下崩 | 阈值化、场景化（基线/峰值/劣化），进 CI 做小样本趋势 | k6 脚本 + 阈值门禁 |
| **线上巡检** | 生产可用性持续可见 | 只读、幂等、可快速定位，独立账号 | 合成监控 |

> **每一条线上缺陷，都应转化为一条自动化用例**——这是把"事故"变成"资产"的唯一低成本路径，也是回归集增长最健康的方式。

## 8. 成本结构：别只看编写

| 成本项 | 内容 | 常被低估的倍数 |
|---|---|---|
| 编写 | 用例设计 + 编码 + 调试 | 基准 1× |
| 维护 | 选择器/接口/数据变更导致的修复 | 2–5× |
| flaky 治理 | 排查不稳定用例、隔离、重跑 | 0.5–1× |
| 环境与数据 | 环境搭建、数据构造与清理 | 0.5–2× |
| 基础设施 | 执行机、并行额度、云设备 | 视规模 |
| 学习与迁移 | 新框架/平台的上手与迁移 | 一次性，但常爆 |

**三条成本控制原则**：

1. **少而准**：100 条覆盖关键路径与历史缺陷的用例，胜过 800 条自动生成的"能跑就行"用例。
2. **靠下层**：把验证压在 L1/L3，UI 只保留 5–10 条旅程。
3. **可观测**：每条用例的执行时长、失败率都要可见，否则无法发现"正在腐烂的 30%"。

## 9. 引入时机：按项目阶段

| 阶段 | 特征 | 该做什么 | 不该做什么 |
|---|---|---|---|
| **0→1 / MVP** | 需求天天变，产品在找方向 | 只写核心算法与金额/状态类的 L1 测试；CI 跑静态检查 + 单元 | 搭平台、写全量 E2E、追求覆盖率 |
| **增长期** | 用户起来，功能稳定，发版变频繁 | 建接口测试主干（L3）+ 少量核心旅程；建立 CI 门禁 | 为每个页面写 E2E |
| **规模化** | 多团队、多服务，发布解耦 | 契约测试、分片并行、报告聚合、flaky 治理；评估平台 | 各团队各搞一套工具 |
| **重构期** | 换框架、拆单体 | 先写特性测试锁行为，再动结构；保留旧测试到切换完成 | 边重构边大规模改测试 |
| **平台期** | 组织级协同成本成为瓶颈 | 上平台、建度量与治理体系 | 指望平台解决用例质量问题 |

> **反直觉但重要**：**MVP 阶段最该写的不是 E2E，而是"算钱、判状态"的单元测试**。因为这类逻辑改了最容易无声出错，且改动最频繁。

## 10. 一页速判表（打分制）

对候选验证点逐项打分（0/1/2），总分 ≥ 7 分即应自动化：

| 问题 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 年执行次数 | < 5 | 5–50 | > 50 |
| 判定确定性 | 只能人工判断 | 部分可判定 | 完全可断言 |
| 出错代价 | 轻微 | 中等 | 高（资金/合规/数据） |
| 变更频率 | 每周大改 | 每月改 | 季度级稳定 |
| 手工执行耗时 | < 5 分钟 | 5–60 分钟 | > 1 小时 |
| 能否在低层证明 | 只能 E2E | 接口层 | 单元层 |
| 有无历史缺陷 | 无 | 偶发 | 曾因此出过线上问题（+3 分） |

**用它做两件事**：①筛选先做哪些；②三个月后回看，判断"当初的判断对不对"。
