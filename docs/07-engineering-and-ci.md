# 07 · 工程架构与 CI

> **适用读者**：工程师、DevOps、测试架构师　|　**前置阅读**：[01 概念与术语](01-concepts-and-terminology.md)、[02 自动化决策](02-when-to-automate.md)　|　**配套实验**：[labs/](../labs/README.md)
>
> 本章回答一个问题：**怎么让"跑测试"变成提交代码后的默认动作，而不是需要商量、提醒、单独排期的额外流程。**
>
> 结论先行：把测试代码当成产品代码来工程化——同一套目录规范、同一套评审、同一套 CI 阶段、同一套报告口径。凡是需要"有人记得去做"的环节，三个月内必然消失。

> 本章的耗时、比例、阈值为**业界经验区间**，用于建立数量级直觉；落地时须用自身 3–6 个月历史数据替换后再定值。

---

## 1. 目标：让"跑测试"成为无需商量的事

判断"是否已经做到"，不看流程文档，看三个可观察现象：

| 判据 | 达标现象 | 未达标现象 |
|---|---|---|
| **默认触发** | 提交即触发，无人手动点"开始" | 需要 QA 在群里喊"帮忙跑一下" |
| **默认阻断** | 红灯无法合并，绕过必须留痕 | 红灯可以先合，事后补测试 |
| **默认可信** | 红灯大概率是真问题，团队立刻去看 | 红灯先重跑，重跑三次再说 |

三者是递进关系：先有触发，阻断才有意义；有阻断，才逼出"红灯必须可信"。**跳过第二步治理 flaky 一定失败**——没人真的在意结果。出现以下任一现象，说明本章是该团队优先级最高的工程工作：MR 里没有测试改动且评审无人提问；本地与 CI 结果不同且无人追查；流水线长期绿灯但线上持续出问题，团队已认为"测试没用"。

## 2. 仓库目录规范

### 2.1 单体仓库（单语言为主）

```
repo/
├── src/order/{service.py, pricing.py}
├── tests/
│   ├── conftest.py                          # 只放跨模块共享的 fixture
│   ├── unit/order/test_pricing.py           # 与被测模块同名，便于双向定位
│   ├── integration/order/test_order_repository.py
│   ├── contract/test_order_api_contract.py
│   ├── e2e/test_checkout_journey.py
│   ├── fixtures/data/orders_valid.json      # 静态数据；小于 1 MB 才入库
│   ├── fixtures/factories/order_factory.py  # 数据工厂，优先于静态文件
│   └── support/                             # 时钟、HTTP 客户端、DB 助手
└── ci/pipeline.yml
```

### 2.2 多语言 / 多服务仓库

```
repo/
├── services/
│   ├── order-api/{src,tests}               # Python：服务内测试跟服务走
│   ├── billing/{internal,billing_test.go}  # Go：测试与被测代码同目录
│   └── web/{src,e2e}                       # TS：仅前端自身旅程
├── tests-e2e/                              # 跨服务旅程：独立顶层，避免归属争议
├── tests-perf/{scenarios,thresholds}       # 性能脚本与阈值基线
└── ci/
```

**跨服务用例必须放顶层 `tests-e2e/`，不要塞进某个服务的 `tests/`。** 否则跨团队排障时两个团队都认为"这条用例不是我们的"。

### 2.3 物理关系与命名

| 模式 | 结构 | 适用 | 代价 |
|---|---|---|---|
| **同目录并存** | `pricing.py` + `pricing_test.go` 同目录 | 编译型语言、单元测试 | 目录噪音；弱约定生态不适用 |
| **镜像树** | `src/order/x.py` → `tests/unit/order/test_x.py` | Python、TS、Java | 重构时两边都要动 |
| **按层 + 镜像模块** | `tests/unit/order/`、`tests/e2e/` | 层间运行方式差异大 | 同模块用例分散多处 |

推荐组合是最后一行：**层决定"怎么跑"（并发度、超时、依赖），模块决定"谁负责"**。命名则按下表对齐生态约定：

| 生态 | 测试文件 | 用例名 | 反例 |
|---|---|---|---|
| Python / pytest | `test_pricing.py` | `test_below_threshold_keeps_amount` | `test1`、`test_ok` |
| TS / Vitest、Playwright | `pricing.spec.ts` | `keeps amount when below threshold` | `works`、`e2e-01` |
| Go | `pricing_test.go` | `TestApplyDiscount_BelowThreshold` | `TestFunc`、`TestA` |
| Java / JUnit | `PricingTest.java` | `keepsAmountWhenBelowThreshold` | `test1`、`testAll` |

命名必须能回答：**在什么条件下、做了什么、期望什么**。做不到就是没想清楚——改名字的过程通常会暴露"这条用例其实在验两件事"。

### 2.4 fixture、工厂与数据文件放哪

- **静态数据** `tests/fixtures/data/`：小于 1 MB 才入库，大文件走对象存储 + 版本号引用
- **数据工厂** `tests/fixtures/factories/`：默认值合法，只对需要差异的字段显式赋值
- **数据库 seed** `tests/fixtures/db/`：只放不可变的字典数据，业务数据一律由工厂造
- **容器编排** `tests/support/containers.py`：端口随机，禁止写死 5432
- **性能基线** `tests-perf/thresholds/`：变更必须走评审，禁止就地改数字

## 3. 测试代码的工程标准

测试代码的第一个读者是**半年后排查失败的人**，不是写代码的人。

### 3.1 AAA 结构与三个"一个"

```python
def test_below_threshold_keeps_amount():
    order = OrderFactory.build(subtotal=99)      # Arrange：只构造与判定相关的最小状态
    total = Pricing.apply_discount(order)        # Act：一个动作，两个 Act 就是两条用例
    assert total == 99                           # Assert：只断言用例名声称的那条规则
```

硬约束：**一个 Act、一个判定焦点、一个失败原因**。"单一断言焦点"不等于"单一 assert 语句"——一条用例断言 5 个字段，失败时只看得到第一个，其余被掩盖；应拆成多条或参数化。`assert resp.ok and resp.data` 这类短路求值同样会隐藏真实原因。

### 3.2 可检验的工程标准

| 标准 | 检验方法 | 违规信号 |
|---|---|---|
| 单条用例 ≤ 30 行（经验区间） | 静态扫描函数行数 | 一条用例要滚三屏 |
| 测试代码无分支 | 扫描 `if` / `for` / `try`（断言内除外） | 用例里出现 `if env == "ci"` |
| 用例之间无依赖 | 随机序跑 10 次全绿 | 单跑通过、全量失败 |
| 不访问真实外网 | 断网或在无出口网络跑一遍 | 加 `--offline` 后大批失败 |
| 不依赖固定睡眠 | 搜索 `sleep(` | `sleep(3)` 后断言，注释"等接口返回" |

### 3.3 确定性四要素

非确定性是 flaky 的唯一来源，必须逐项封死：

| 维度 | 失败症状 | 正确做法 | 错误做法 |
|---|---|---|---|
| **时间** | 月末、跨年、时区切换日失败 | 注入 `Clock`，用例内冻结时间 | 直接调 `datetime.now()` |
| **随机** | 偶发失败且无规律 | 固定 seed，并把 seed 打进日志 | 随机造数据且不记录 seed |
| **网络** | 峰值时段失败，重跑通过 | 外部依赖全部走替身 | 断言第三方沙箱环境 |
| **并发** | 并行度提高后失败率上升 | 每次运行独立命名空间 | 并行 worker 共用同一账号 |
| **顺序** | 集合遍历顺序影响输出 | 显式排序后再断言 | 断言 `list(set(...))` 的顺序 |
| **本地化** | 只在 CI 失败，报格式差异 | 固定 `TZ=UTC`、`LC_ALL=C` | 依赖开发机 locale |

> 判断标准很硬：**同一 commit 连跑 20 次，必须 20 次同结果。** 做不到就不是"环境问题"，是这条用例有缺陷。

## 4. 测试数据治理

数据是 flaky 与"环境问题"的最大单一来源。

### 4.1 数据隔离三原则

| # | 原则 | 违反后的症状 | 落地方式 |
|---|---|---|---|
| **1** | **共享只读、独享可写**：会被修改的数据必须由本次运行创建 | 用例 A 改的数据被 B 读到，随机失败 | 字典数据可共享；业务实体一律工厂创建 |
| **2** | **隔离维度是"运行"而非"环境"** | 两个 MR 同时跑，互相清库 | 注入 `RUN_ID`，作为租户 / Schema / 前缀 |
| **3** | **谁创建谁回收，且回收能兜底** | 库表膨胀、唯一约束冲突累积 | 正常路径 teardown；异常路径靠命名空间过期清理 |

### 4.2 数据工厂优先于静态数据集

```python
class OrderFactory:
    @classmethod
    def build(cls, **overrides):
        base = {"id": ulid(), "subtotal": 100, "status": "created",
                "tenant": current_run_id()}
        return Order(**{**base, **overrides})
```

三个要求：**默认值合法**（不传参就能落库）、**唯一性内建**（`id`、`email` 默认带运行 ID 前缀）、**差异显式**（用例只写与判定相关的字段）。

### 4.3 各类数据的处置策略

| 数据类别 | 构造方式 | 隔离粒度 | 回收 | 典型事故 |
|---|---|---|---|---|
| 字典/枚举 | 迁移脚本预置 | 全局共享 | 不回收 | 有人手工改一条，所有环境不一致 |
| 业务实体 | 数据工厂 | 每次运行 | teardown 删除 | 用固定 ID，并行时主键冲突 |
| 用户与权限 | 工厂 + 运行时注册 | 每次运行 | 过期清理任务 | 共用 `test_user`，权限互相覆盖 |
| 文件/对象存储 | 运行时上传 | 运行前缀 | 生命周期规则 | 同一个 key，后跑的覆盖先跑的 |
| 消息队列 | 运行时建 topic | 运行前缀 | 自动过期 | 共享队列，消费到别人的消息 |

**脱敏与合规**：生产数据不得直接进测试环境；需要真实分布时用"结构保留 + 值替换"生成，保留字段级映射以备排障。录制回放报文入仓前必须过敏感字段过滤（手机号、证件号、token、卡号），过滤规则版本化。凭据一律走 CI 密钥注入，代码里只出现变量名。

**禁止共享固定账号**：它带来三类无法排查的问题——并发登录互踢、权限被他人改动、审计归属混乱。替代方案按成本排序：每次运行注册独立账号 → 账号池 + 租约 → 只读共享、写操作独立账号。

## 5. 测试环境治理

### 5.1 环境分层

| 层 | 目的 | 数据 | 谁维护 | 允许跑什么 | 刷新 |
|---|---|---|---|---|---|
| **本地** | 秒级反馈 | 容器内临时数据 | 开发者 | L1、L2 | 每次运行重建 |
| **CI 临时环境** | 可信判定 | 每次运行新建 | 流水线 | L1–L4 | 运行结束销毁 |
| **预发 / Staging** | 发布前验证、联调 | 脱敏的准生产数据 | 环境 owner | L3–L5 | 每日或按需重置 |
| **线上灰度** | 真实流量下验证 | 生产数据 | SRE | 合成监控、少量拨测 | 不重置 |

**环境数量不是成熟度标志，"环境能不能被重建"才是。** 一个 20 分钟内可从零重建的环境，胜过早就绪但无人敢动的三个祖传环境。

### 5.2 环境即代码

```yaml
# docker-compose.test.yml 关键片段
services:
  db:
    image: postgres:16
    ports: ["0:5432"]                 # 随机端口，禁止写死，避免并行冲突
    tmpfs: /var/lib/postgresql/data   # 内存盘：快，且天然隔离
```

进程内方案（testcontainers、Spring Boot Test）优于长期存活的共享环境，理由只有一条：**它把"环境状态"变成测试代码的一部分，跟随版本走**。

### 5.3 外部依赖替身策略

| 依赖类型 | 推荐替身 | 不推荐 | 理由 |
|---|---|---|---|
| 支付/银行 | 官方沙箱 + 录制回放兜底 | 真实生产接口 | 有资金风险；沙箱不稳时用回放 |
| 短信/邮件 | 本地 SMTP / 假网关 | 真实发送 | 成本高且无法断言 |
| 第三方开放 API | 录制回放（VCR） | 每次真实调用 | 限流、变更、延迟不可控 |
| 内部服务（强依赖） | 契约测试 + 桩服务 | 全链路真调 | 联调放大失败面 |

录制回放的边界：**只用于"稳定、低频变更、难以本地复现"的外部依赖**。把回放用在自己的服务间接口上，会让契约漂移完全不可见。

### 5.4 环境漂移的症状与处置

| 症状 | 可能原因 | 处置动作 |
|---|---|---|
| 同一 commit 昨天绿今天红 | 环境被手工改动 | 环境纳入 IaC；禁用控制台改配置 |
| 只有某台执行机失败 | 执行机镜像版本不一致 | 镜像打版本号，禁止 `latest` |
| 用例依赖执行顺序才通过 | 数据库残留数据 | 每次运行独立 Schema |
| 本地绿、CI 红，差异在时间格式 | 时区 / locale 不同 | 统一 `TZ=UTC`、`LC_ALL=C` |
| 失败信息里出现他人数据 | 共享库无隔离 | 立即上运行级命名空间 |

## 6. CI 阶段设计

### 6.1 双轨制

**快轨**给反馈，**慢轨**给信心。目标不同，不能合成一条。

```
                 ┌── 快轨：每次 push，目标 ≤ 5 min（经验区间）────────┐
commit / MR ────►│ ① lint/type ─► ② unit ─► ③ contract(轻量)         ├─► ⛔ 快轨门禁 ─► 允许合并
                 └────────────────────────────────────────────────────┘

                 ┌── 慢轨：合并后 / 定时 / 发布前，目标 ≤ 45 min ──────┐
合并到 main ────►│ ④ integration ─► ⑤ e2e ─► ⑥ perf ─► ⑦ security    ├─► ⛔ 发布门禁 ─► 允许发版
                 └────────────────────────────────────────────────────┘
```

### 6.2 阶段划分与失败语义

| 阶段 | 内容 | 目标耗时（经验区间） | 失败阻断 | 可否重跑 |
|---|---|---|---|---|
| ① 静态检查 | lint、格式化、类型检查、依赖漏洞扫描 | 30 s – 2 min | 是 | 否（改代码） |
| ② 单元 | L1 全量 | 1 – 4 min | 是 | 否 |
| ③ 接口/契约 | L2/L3 主干 + 契约兼容性 | 2 – 8 min | 是 | 有条件（§9.3） |
| ④ 组件集成 | 服务 + 真实 DB / 缓存 / MQ | 5 – 15 min | 是 | 有条件 |
| ⑤ E2E | 核心旅程，少量 | 5 – 20 min | 是（发布门禁） | 有条件 |
| ⑥ 性能 | 关键场景 + 阈值断言 | 10 – 40 min | 是（发布门禁） | 是（需对比基线） |
| ⑦ 安全 | SAST、依赖扫描、轻量 DAST | 5 – 20 min | 高危必阻断 | 否 |

**成本递增原则**：阶段按单次运行成本从低到高排列——静态检查 30 秒能发现的问题，不值得让 E2E 跑 20 分钟才发现。

**失败快速退出**：阶段内 `--maxfail=1` 适合快轨（会掩盖同阶段其他失败）；慢轨改为**分片内快速失败、跨分片不互相取消**，一次拿到与分片数等量的失败样本；资源受限时可让快轨失败则不启动慢轨，但主干分支例外——主干需要完整失败画像。

### 6.3 缓存与依赖预装

```yaml
# 关键片段：只给结构，不给完整流水线
stages: [static, unit, contract, integration, e2e, perf, security]
cache:
  key: "${LOCKFILE_SHA}-${RUNTIME_VERSION}-${IMAGE_TAG}"
  paths: [".venv", "~/.cache/ms-playwright", ".mypy_cache"]
fail_fast: shard-local        # 分片内快速失败，分片间不互相取消
```

三条规则：**key 必须含锁文件哈希**（否则依赖升级后仍命中旧缓存，出现"本地能跑 CI 不能跑"）；**不缓存测试产物与数据库**（等于缓存了上次的通过状态）；**缓存 miss 必须降级而非失败**（否则缓存服务抖动会变成红灯）。

## 7. 并行与分片

### 7.1 切分维度与不均处置

| 策略 | 做法 | 适用规模 | 主要缺点 |
|---|---|---|---|
| 按文件 | 每个文件一片 | < 500 条 | 大片小片差异可达 10 倍 |
| 按标签 | `@smoke`、`@p0` 分片 | 任意 | 标签易失真、需维护 |
| 按历史耗时 | 用最近 N 次耗时装箱 | > 500 条 | 新用例无基线 |
| 动态队列 | 执行机空闲即取下一条 | > 1000 条 | 需调度器支持 |

用例规模过千后，静态切分的不均会造成 **30%–50% 的墙钟时间浪费**（经验区间）。处置：把 top 5 长尾用例单列"长尾片"；按层切分并对不同层设不同并发度；分片清单由脚本生成，禁止手工维护；若加机器而总时长不变，说明存在串行瓶颈（共享账号、单实例 DB、全局锁），先解争用再加机器。

### 7.2 执行机数量估算

```
所需执行机数 ≈ ceil(串行总耗时 ÷ 目标墙钟时间) × 安全系数
  串行总耗时：最近 20 次运行的 P50（不要用平均值，长尾会拉高）
  安全系数：1.2 – 1.5（覆盖分片不均、镜像拉取、排队）
```

算例：串行 42 min、慢轨目标 10 min → `ceil(4.2)=5` → `5 × 1.3 ≈ 7` 台。**上限约束**：不超过数据与环境能支撑的并发上限；超过后加机器只会提高 flaky 率，此时应先解决隔离（§4）。

### 7.3 并发下的数据冲突

并发失败有三个特征：**只在并行时出现、重跑常通过、错误信息指向数据而非逻辑**。排查顺序固定为：共用固定账号/ID/文件名 → 断言了全局计数（"总数应为 12"）→ 依赖创建顺序（自增 ID、时间戳排序）→ 外部依赖限流。

## 8. 报告聚合与制品

### 8.1 JUnit XML 作为统一口径

理由不是它好看，而是**所有 CI 与平台都能解析它**，换工具不换口径。

| 字段 | 要求 | 常见错误 |
|---|---|---|
| `testsuite@name` | 阶段名 + 分片号 | 全写成 `pytest`，聚合后无法区分 |
| `testcase@name` | 稳定用例 ID（重命名不改 ID） | 用随机参数做名字，历史趋势断裂 |
| `failure@message` | 一行结论 + 期望 / 实际 | 只有 `AssertionError`，需点进日志 |
| `properties` | `run_id`、`shard`、`commit`、`env` | 缺失，无法做跨维度下钻 |

### 8.2 制品归档策略

| 制品 | 产生阶段 | 保留期（经验区间） | 用途 |
|---|---|---|---|
| 控制台日志 | 全阶段 | 7 – 14 天 | 快速排障 |
| JUnit XML | 全阶段 | 90 天 | 趋势、门禁判定 |
| trace / 录屏 | E2E **失败**用例 | 14 – 30 天 | 复现 UI 问题 |
| 性能报告与基线对比 | 性能 | 90 天 | 性能回归判定 |
| 发版门禁证据包 | 发布前 | 1 年以上（不可变归档） | 审计 |

体积治理三条：**只保留失败用例的 trace 与录屏**、**日志按行数截断并保留首尾**、**采样保留少量成功样本用于对比**。

## 9. flaky 治理闭环

flaky 的危害不是多花几分钟，而是**训练整个团队忽略红灯**（见 [10 §C2](10-anti-patterns.md)）。

### 9.1 检测与分类

检测按成本从低到高：**历史统计**（30 天内同用例失败/通过比，最先做，直接给出 flaky 排行榜）→ **随机序**（关闭固定顺序跑 10 轮，查顺序依赖）→ **重复运行**（同 commit 连跑 10–20 次，用于关键用例集）→ **多分片对比**（同一用例在不同分片各跑一次，查数据冲突）。

| 类别 | 典型症状 | 快速判定 | 经验占比 |
|---|---|---|---|
| 时序/等待 | 只在慢机器失败，加超时后通过 | 人为降速可稳定复现 | 30% – 40% |
| 数据 | 单跑通过、全量失败，与顺序相关 | 随机序跑 10 次 | 20% – 30% |
| 环境 | 高并发时失败，报资源类错误 | 降并发重跑 | 10% – 15% |
| 外部依赖 | 错误在边界，含超时/限流码 | 看错误码与时间分布 | 10% – 15% |
| **真 bug** | 竞态、幂等缺失、错误处理缺失 | 注入延迟或提高并发可稳定复现 | 5% – 10% |
| 用例错误 | 断言过时、选择器不准 | 人工读代码 | 5% – 10% |

> 占比为**业界经验区间**，随技术栈差异极大，仅用于判断"先修哪一类"。**"真 bug"最容易被误判为 flaky**：它看起来也偶发，但它是唯一会流到线上的那类。

### 9.2 处置流程

```
                  ┌─ 否 ─► 稳定失败：走普通缺陷流程（不隔离、不重跑）
                  │
发现红灯 ─► 重跑 ─┤      ┌─ 否 ─► 记为环境抖动，累计 3 次转隔离
                  └ 是 ─► 同 commit 连跑 10 次，失败 ≥ 1 次？
                              ├─ 是 ─► 可复现？─ 是 ─► 定位根因 ─► 修 ─► 回归
                              │                └ 否 ─► 进 quarantine 隔离区
                              │                          ├─ 7 天内修复 ─► 出区
                              │                          └─ 超期 ─► 删用例 + 留缺陷记录
                              └─ 否 ─► 判定稳定通过，回主集
```

### 9.3 自动重跑的正确与错误用法

| 用法 | 场景 | 判定 |
|---|---|---|
| 失败后重跑 1 次，两次都失败才报红 | 吸收基础设施抖动 | **正确**，但必须统计重跑率 |
| 重跑 2–3 次，任一次通过即绿 | "提高稳定性" | **错误**，等于把 flaky 合法化 |
| 门禁失败后手工重跑直到绿 | 赶发布 | **错误**，必须留痕并计入绕过次数 |

原则：**重跑只能用于"疑似基础设施问题"，且重跑率必须作为指标暴露**。重跑率升到 5% 以上（经验区间），说明基础设施或用例质量已有系统性问题。

### 9.4 quarantine 隔离区的纪律

隔离项**不阻断门禁，但必须计入 flaky 率**（否则等于隐藏问题）；每项必须有 owner 与到期日，缺失自动升级到平台负责人；规模设硬上限（如 ≤ 总用例数 2%，经验区间），超限冻结新增；**隔离区空了才算治完**——它是临时病房，不是仓库。

## 10. 门禁与流水线的常见工程坑

| 坑 | 表现 | 为什么危险 | 对策 |
|---|---|---|---|
| **重跑掩盖问题** | 红灯重跑几次就绿，无人追查 | 把真实缺陷训练成"正常现象" | 重跑留痕，重跑率进周报 |
| **超时阈值拍脑袋** | 超时设 5 s，CI 机器慢时正常请求也超时 | 制造大批假失败，团队开始无视红灯 | 用 P99 × 2 定阈值，随基线更新 |
| **缓存导致假绿** | 依赖已升级但命中旧缓存 | 本地红、CI 绿，问题延后到线上 | key 含锁文件哈希；定期无缓存跑一次 |
| **只在主干跑慢轨** | MR 阶段只跑快轨 | 问题合并后才暴露，回滚成本翻倍 | MR 跑受影响模块的慢轨子集 |
| **报告只留最后一个分片** | 聚合用例数少于实际 | 门禁判定基于残缺数据 | 每分片独立输出 XML，聚合全量拉取 |
| **skip 无登记** | `@pytest.mark.skip` 随手加 | 用例静默死亡，覆盖率虚高 | skip 必须带原因与工单号，纳入巡检 |
