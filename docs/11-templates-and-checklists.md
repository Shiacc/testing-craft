## 1. 用例设计模板

### 1.1 用例卡（新增用例必填）

| 字段 | 填写要求 | 示例 |
|---|---|---|
| 用例 ID | `模块-序号`，永久不变 | `PRICE-012` |
| 标题 | 一句话说清"在什么条件下验证什么" | 会员折扣后金额低于门槛时满减券不生效 |
| 关联风险 | 对应哪条业务规则 / 哪个历史缺陷 / 哪个监管条款 | 规则 R3（叠加顺序）、缺陷 #1042 |
| 前置条件 | 数据、账号、状态 | 金卡用户，购物车 1 件 100.00 元 |
| 判定标准 | **可断言**，不能写"显示正常" | 应付金额 = 90.00，券抵扣 = 0.00 |
| 层级 | L1 / L2 / L3 / L4 / L5 | L1 |
| 自动化 | 是 / 否 / 暂缓（写原因） | 是 |
| 归属 | 谁负责维护 | team-pricing |

### 1.2 判定标准的写法对照

| 模糊写法（不可用） | 可断言写法（可用） |
|---|---|
| "金额显示正确" | "应付 = `¥90.00`，且与后端 `payable` 字段一致" |
| "页面正常加载" | "HTTP 200，`items` 非空，首屏渲染时间 < 2s" |
| "性能可以接受" | "p95 < 200ms，错误率 < 1%" |
| "错误提示友好" | "提示文案包含'未达门槛'，且 `data-testid=coupon-hint` 存在" |
| "并发下没问题" | "50 并发 × 200 次请求，错误率 0%，无 5xx" |

> 写不出可断言的标准，说明这个用例**还不该自动化**（[02 §5](02-when-to-automate.md)）。

## 2. 自动化用例代码评审清单

新增或修改测试代码时逐项勾选（可直接放进 PR 模板）：

- [ ] **1. 单一焦点**：一条用例只验证一个业务结论；参数化覆盖多组数据，而不是复制粘贴
- [ ] **2. AAA 结构**：准备 / 执行 / 断言 三段清晰，读起来像一段业务描述
- [ ] **3. 断言有效**：断言的是业务结果，不是"函数被调用过"或"没有抛异常"
- [ ] **4. 无顺序依赖**：单独执行、乱序执行、与其他用例并发执行都必须通过
- [ ] **5. 数据自造**：不依赖"数据库里已存在的那条记录"或共享账号
- [ ] **6. 确定性**：不依赖当前时间、随机数、网络抖动；必要时注入固定种子/时钟
- [ ] **7. 无 `sleep`**：用自动等待或显式轮询，不用固定等待
- [ ] **8. 失败可读**：断言失败信息能直接指出"期望 vs 实际"
- [ ] **9. 选择器稳定**：UI 用 `data-testid`，不用样式类名或文案
- [ ] **10. 无过度 mock**：不 mock 被测对象内部实现，只在外部边界打桩
- [ ] **11. 有标记**：打了正确的 marker/标签（smoke / edge / slow），能被 CI 选择
- [ ] **12. 缺陷可追溯**：回归用例注明缺陷编号与原因

> 12 项里最容易漏的是 4、5、7，而它们正好是 flaky 的三大来源（[07 §9](07-engineering-and-ci.md)）。

## 4. 平台需求清单（RFP 用）

采购或自建评审时逐项要求供应商/团队给出**证据**，而不是"支持/不支持"的口头回答。

| # | 能力域 | 具体要求 | 档位 | 证据要求 |
|---|---|---|---|---|
| 1 | 资产管理 | 用例集中存储、目录、标签、版本、跨项目复用 | 必选 | 现场演示 + 权限模型说明 |
| 2 | 资产管理 | 用例变更历史与回滚 | 可选 | 截图 + 操作日志样例 |
| 3 | 调度执行 | 定时 / 按需 / API 触发 | 必选 | 提供 API 文档并现场调用 |
| 4 | 调度执行 | 分布式分片、并发控制、失败重试策略可配 | 必选 | 分片 4 份的实测耗时对比 |
| 5 | 调度执行 | 执行机（agent）注册、健康检查、自动摘除 | 必选 | 演示杀掉一个 agent 后的表现 |
| 6 | 环境管理 | 多环境配置、环境隔离与回收 | 必选 | 两套环境并行跑互不干扰 |
| 7 | 设备矩阵 | 真机/浏览器矩阵、并行额度 | 视需求 | 列出可用机型与并发上限 |
| 8 | 结果报告 | 聚合报告、历史趋势、失败归因 | 必选 | 近 10 次运行的趋势图 |
| 9 | 结果报告 | 日志 / 录屏 / trace 归集与保留策略 | 必选 | 打开一条失败用例的现场 |
| 10 | 质量门禁 | 阈值规则、阻断发布、与流水线联动 | 必选 | 配置一条规则并触发阻断 |
| 11 | 权限审计 | 角色权限、操作留痕、合规导出 | 视合规 | 导出一次审计日志 |
| 12 | 流程集成 | 需求—用例—缺陷—发布 双向追踪 | 可选 | 展示一条需求的全链路 |
| 13 | 低代码 | 非开发者可编写/维护用例 | 可选 | 让一名业务同学现场写一条 |
| 14 | 测试数据 | 数据构造、脱敏、回收、数据集版本 | 可选 | 演示数据工厂或等价能力 |
| 15 | 开放能力 | 开放 API、插件机制、自定义报告 | 必选 | 提供 API 清单与调用示例 |

> **16 项里若有 3 项以上"必选"拿不出证据，就不要进入商务谈判阶段。**

## 5. 平台上线 Go / No-Go 检查表

上线前逐项确认，任一红项即 No-Go：

**A. 资产（4 项）**

- [ ] 至少 300 条用例已完成迁移并在平台内稳定运行 2 周
- [ ] 每条用例有明确 owner（无主用例数为 0）
- [ ] 用例目录、标签体系已定，且与新用例约定一致
- [ ] 存量用例导出路径已验证（能导出并脱离平台运行）

**B. 执行（4 项）**

- [ ] 执行机池容量覆盖峰值并发（含 30% 余量）
- [ ] 单次全量执行墙面耗时在团队可接受范围内（通常 < 30 分钟）
- [ ] 失败用例的日志/trace 可在平台内直接查看，无需登录执行机
- [ ] 平台自身故障时的降级路径已演练（如直接跑 CI 脚本）

**C. 治理（4 项）**

- [ ] 门禁规则 ≤ 3 条，且每条都有明确负责人与豁免流程
- [ ] 权限模型已配置（谁能改用例、谁能放行、谁能改门禁）
- [ ] flaky 隔离区（quarantine）已建立，且有出区条件与期限
- [ ] 度量口径已对齐（逃逸缺陷、flaky 率、墙面耗时定义唯一）

**D. 运营（3 项）**

- [ ] 有具名平台 owner（0.5-1 FTE），不是"兼任"
- [ ] SLA 已定义（可用性、排队时长、故障响应）
- [ ] 上线后 30 天的运营节奏已排期（周会看红灯、月度复盘）

> 详细判据与失败模式见 [04 §7-8](04-test-platforms.md)。

## 6. 门禁规则模板

```yaml
# 质量门禁：少而硬。每条规则都必须能回答"为什么是这条阈值"
gate:
  version: 1
  rules:
    - id: static-clean
      name: 静态检查零告警
      stage: fast
      when: [pull_request, push]
      assert: lint_errors == 0
      blocking: true
      owner: team-platform

    - id: core-green
      name: 核心链路全绿（单元 + 接口 + UI 冒烟）
      stage: fast
      when: [pull_request, push]
      assert: failed_tests == 0
      blocking: true
      owner: team-quality
      timeout_s: 300

    - id: perf-no-regression
      name: 性能不退化
      stage: slow
      when: [push:master]
      assert: p95_ms < 200 and error_rate < 0.01
      blocking: true
      owner: team-platform
      baseline: last_5_runs_median   # 与基线比较，避免绝对值阈值随机器漂移

  exemptions:
    # 豁免必须留痕：谁、为什么、有效期
    require:
      - requester
      - reason
      - expires_at   # 最长 7 天，到期自动恢复
```

**三条设计原则**（[08 §5](08-metrics-and-quality-gates.md)）：少而硬、可解释、5 分钟内能跑完。
门禁超过 5 条时，先删掉最常被豁免的那两条。

## 7. 度量口径卡模板

每个指标一张卡，杜绝"两个部门报两个数"：

| 字段 | 内容 |
|---|---|
| 指标名 | 逃逸缺陷率 |
| 一句话定义 | 未被测试拦截、流入生产后才被发现的缺陷占比 |
| 计算式 | 逃逸缺陷数 ÷（逃逸缺陷数 + 测试阶段发现缺陷数） |
| 数据源 | 缺陷系统（`found_in` ∈ {prod, gray}）+ 发版记录 |
| 统计窗口 | 按自然月，发版后 14 天内计入 |
| 排除项 | 需求变更导致的行为调整；第三方服务故障；已知且已登记的风险 |
| 目标区间 | < 10%（业界经验区间，须用自身 3-6 个月基线替换） |
| 责任人 | team-quality（唯一口径负责人） |
| 阈值动作 | > 15% 连续两个月 → 启动专项复盘（[§8](#8-逃逸缺陷复盘模板)） |

> 指标定义必须**唯一且不可协商**。允许争论"目标定多少"，不允许争论"怎么算"。

## 10. 季度用例巡检表

每季度对存量用例做一次"删 / 改 / 留"决策（[09 §4](09-organization-and-governance.md)）：

| 判据 | 动作 |
|---|---|
| 连续 2 个季度未失败，且对应代码已删除 | **删** |
| 因需求变更已不成立 | **删**，并在需求/缺陷里留痕 |
| flaky 率 > 5% | **改**（限期 2 周）或**隔离**，不得静默重跑 |
| 断言过弱（无业务结论） | **改** |
| 覆盖历史缺陷 | **留**，标注缺陷编号 |
| 覆盖核心链路 | **留**，纳入 smoke |

巡检产出：`删 N 条 / 改 M 条 / 隔离 K 条`，以及"本季度用例总数变化与逃逸缺陷趋势的对照"。
