# 08 · 度量与质量门禁

> **适用读者**：QA 负责人、研发管理者、测试架构师　|　**前置阅读**：[01 概念与术语](01-concepts-and-terminology.md)、[07 工程架构与 CI](07-engineering-and-ci.md)
>
> 本章回答两个问题：**怎么证明测试投入值这个钱；怎么把"能不能发版"变成一个不用开会争论的判断。**
>
> 结论先行：结果指标证明价值，健康指标决定可持续性，过程指标只用来定位瓶颈。任何被当作个人考核项的指标都会在三个月内失效。

> 本章所有目标区间、比例为**业界经验区间**，用于建立数量级直觉；落地时须用自身 3–6 个月历史数据替换后再设阈值。

---

## 1. 度量的目的

度量只服务两件事：**解释钱花得值不值**、**决定下一步投哪**。只要一个指标不服务于这两件事，它就不该出现在看板上。

| 度量能回答 | 度量不能回答 |
|---|---|
| 我们的测试是否拦住了该拦的问题 | 某位工程师是否努力 |
| 哪一层是当前的瓶颈 | 团队是否"重视质量" |
| 投入产能后是否真有改善 | 测试用例写得好不好（要看断言） |
| 门禁是否在被绕过 | 该不该上测试平台（见 [04](04-test-platforms.md)） |

一条指标上板前，先过下面四问，任一不过就不要上：

| 属性 | 要求 | 不合格的例子 |
|---|---|---|
| **口径稳定** | 分子分母写死，跨季度可比 | 中途改了"用例数"的统计方式，趋势线断裂 |
| **可追溯** | 能下钻到具体用例、缺陷或流水线运行 | 只有一个汇总百分比 |
| **可归因** | 异常时能定位到团队或模块 | "全公司通过率 87%"，无人能认领 |
| **可行动** | 异常能对应一个具体动作（见 §8） | "质量指数 76 分"，无定义无动作 |

**考核化是度量失效的最快路径**：一旦指标进入绩效，被度量者会优化数字而不是优化系统，这在 §3 有完整的机制说明。制定指标前先确认：这个数字变好时，用户是否真的更少遇到故障？答不上来就不要用。

## 2. 三层指标

三层的关系是：**结果指标是目的，健康指标是刹车，过程指标是仪表盘**。缺结果指标会被质疑价值，缺健康指标会用短期压榨换取数字，缺过程指标则无法定位瓶颈。

**落地顺序**：先只采三个——逃逸缺陷率、快轨 P95 时长、flaky 率。前两个决定"要不要继续投"，第三个决定"已投的东西还能不能用"。指标一多，维护口径的人力会超过分析收益（经验区间：看板超过 8 个指标后，周会实际使用率明显下降）。

### 2.1 结果指标（给管理层看）

| 指标 | 定义 | 算法 | 口径陷阱 | 目标区间 |
|---|---|---|---|---|
| **逃逸缺陷率** | 测试未拦住、流入生产或被用户发现的缺陷占比 | 逃逸缺陷数 ÷ 本周期交付缺陷总数 | 只统计"被用户报的"，漏掉监控与客服渠道发现的 | < 15%，核心链路 < 5% |
| **变更失败率** | 导致回滚、热修或事故的变更占比 | 失败变更数 ÷ 总变更数 | 只算发版不算配置变更，数字会虚低 | 10% – 15% |
| **MTTR** | 从故障发生到恢复服务的时长 | 恢复时间 − 发现时间（取 P50 与 P90） | 用"修复完成"代替"服务恢复"，数字虚高 | P50 < 1 h，P90 < 4 h |
| **线上事故数** | 按严重度分级的事故计数 | 按月统计 P0 / P1 | 分级标准不写死，跨月不可比 | 逐季下降，P0 为 0 |

### 2.2 过程指标（给工程团队看）

| 指标 | 定义 | 算法 | 口径陷阱 | 目标区间 |
|---|---|---|---|---|
| **流水线时长** | 快轨与慢轨各自的墙钟时长 | 取 P50 与 P95，不用平均值 | 平均值掩盖长尾，团队感知的是 P95 | 快轨 ≤ 5 min，慢轨 ≤ 45 min |
| **通过率** | 流水线运行中通过的比例 | 通过次数 ÷ 总运行次数 | 重跑后的"最终通过"会美化数字 | 主干 ≥ 95% |
| **关键路径自动化覆盖数** | 被自动化覆盖的业务关键路径条数 | 按业务方确认的关键路径清单逐条勾 | 只数"有脚本"，不数"脚本能判定对错" | 100% 覆盖 P0 路径 |

过程指标只用于**定位瓶颈**，不用于评价团队。它们变化快、易操纵，且与用户价值没有直接因果。

### 2.3 健康指标（决定明年还在不在）

| 指标 | 定义 | 算法 | 口径陷阱 | 目标区间 |
|---|---|---|---|---|
| **flaky 率** | 结果不稳定的用例占比 | flaky 用例数 ÷ 总用例数（30 天窗口） | 只算"进过隔离区"的，漏掉被重跑掩盖的 | < 2% |
| **重跑率** | 需要重跑才通过的运行占比 | 含重跑的运行数 ÷ 总运行数 | 不统计就没有，越晚统计越难补 | < 5% |
| **用例维护成本** | 每月花在修用例上的人时 | 按工单标签汇总人时 ÷ 百条用例 | 只算显性工单，漏掉"顺手改一下" | 基线化，逐季下降 |
| **用例存活率** | 12 个月前写的用例现在还在跑且有效的比例 | 存活用例数 ÷ 12 个月前用例总数 | 存活 ≠ 有效，需配合"近 90 天有失败记录或断言仍匹配" | > 70% |
| **执行稳定性** | 同一 commit 多次运行结果一致的比例 | 结果一致的运行组 ÷ 总运行组 | 样本太少时波动大，至少 20 组 | > 98% |

> 这五个数字一起看才有意义：**flaky 率低但重跑率高**，说明重跑在掩盖问题；**存活率高但维护成本高**，说明用例在持续还技术债。

### 2.4 指标口径卡

每个上板指标配一张口径卡。没有口径卡的指标，三个月内必然出现"两个部门报出两个数"，然后整块看板失去信任。

| 字段 | 示例（逃逸缺陷率） |
|---|---|
| 要回答的问题 | 我们的测试是否拦住了该拦的问题 |
| 算法 | 逃逸缺陷数 ÷ 本周期交付缺陷总数 |
| 数据源 | 缺陷系统的发现渠道字段 + 发布记录 |
| 统计窗口 | 自然月，按缺陷发现时间归月 |
| 排除项 | 需求变更导致的"缺陷"、第三方故障 |
| 责任人 | QA 负责人定口径，数据工程取数 |
| 阈值与动作 | > 15% 触发月度复盘（见 §8） |

## 3. 明确"不要用"的指标

| 指标 | 为什么会被 gaming | 典型手法 | 替代 |
|---|---|---|---|
| **用例数量** | 数量与拦住的缺陷无关，越写越多是负担 | 把一条用例拆成十条参数化用例；为凑数写无断言的用例 | 关键路径覆盖数 + 逃逸缺陷率 |
| **代码覆盖率（作为考核项）** | 覆盖率只证明"被执行过"，不证明"被验证过" | 无断言用例、`assert True`、构造无用调用 | 变异得分 + 关键模块覆盖率地图 |
| **自动化率** | 分母可调（把手工用例移出统计），且不区分价值 | 把探索性测试"登记"为自动化；把 UI 脚本重复计数 | 自动化覆盖的关键路径数 |
| **缺陷数量（对个人）** | 提缺陷有奖则滥提，罚缺陷则瞒报 | 拆缺陷、改严重度、线下沟通不上单 | 逃逸缺陷率（团队级） |

共同的失败机制是**古德哈特定律**：当一个度量变成目标，它就不再是好的度量。判断某指标能否使用，问三个问题：

1. 分子分母能否被被考核者单方面调整？
2. 数字变好是否可能不伴随系统变好？
3. 该指标是否只看得到"做了多少"，看不到"拦住了什么"？

任一为"是"，就只能用于观察，不能用于考核。

**团队级与个人级的边界**：逃逸缺陷率、变更失败率这类指标，只有在**团队 ≥ 5 人的统计单元**上才稳定；拆到个人时噪声远大于信号，且必然诱发瞒报。个人级只适合用"是否按约定完成了动作"这类二值指标（提交时是否带测试、flaky 是否按期修完）。

## 4. 覆盖率的正确用法

覆盖率的价值不在数字，而在**它标出的空白区**。正确用法是把它当地图，而不是当成绩单：

| 用法 | 正确 | 错误 |
|---|---|---|
| 定位盲区 | 按模块看未覆盖分支，判断"这些分支是否真的走不到" | 只盯总体百分比 |
| 判断风险集中度 | 核心支付模块覆盖率 45% → 立项补齐 | 全仓库拉平到 60% 就算达标 |
| 配合变异测试 | 对核心模块跑变异，得分低说明断言无力 | 用高覆盖率解释"测试很充分" |
| 作为趋势参考 | 覆盖率骤降 10 个点 → 查是否新代码没写测试 | 覆盖率涨了就认为质量提升 |

三个数字的组合判读（均为**业界经验区间**，需用自身历史数据校准）：

| 现象 | 判读 | 动作 |
|---|---|---|
| 覆盖率高、变异得分低（< 50%） | 断言形同虚设 | 补断言，而非补用例 |
| 覆盖率低、变异得分高 | 覆盖集中且有力，但盲区大 | 按风险补关键路径 |
| 覆盖率高、逃逸缺陷率高 | 测的不是用户真正走的路 | 重画关键路径清单 |
| 三者都低 | 测试尚未形成有效约束 | 从 P0 路径开始重建（见 [02](02-when-to-automate.md)） |

**变异测试的落地方式**：只对核心模块跑（全仓跑成本过高），得分按模块分级判断——核心账务/支付类偏高，一般业务偏低（经验区间：前者 ≥ 70%，后者 50%–60%），具体阈值须用自身历史基线校准。变异得分低但覆盖率高的模块，是"假测试"最集中的地方。

## 5. 质量门禁设计

### 5.1 四条设计原则

| 原则 | 含义 | 违反后果 |
|---|---|---|
| **少而硬** | 单条流水线 ≤ 3 条阻断项 | 门禁越多，绕过文化越强 |
| **可解释** | 失败必须能一句话说清"为什么被拦、怎么改" | 团队只会找平台负责人问 |
| **5 分钟内可判定** | 门禁判定本身不能成为瓶颈 | 为了赶发版而手工跳过 |
| **失败必阻断** | 无"告警模式"长期存在 | 门禁退化为装饰 |

### 5.2 门禁候选清单

| 候选门禁 | 判定口径 | 建议所在轨 | 备注 |
|---|---|---|---|
| 静态检查 0 告警 | lint/type 告警数 = 0 | 快轨 | 存量告警用基线冻结，只拦新增 |
| 单元通过率 100% | 无失败、无 error | 快轨 | 允许 skip，但 skip 必须登记 |
| 接口/契约通过率 100% | 无失败；契约无破坏性变更 | 快轨 | 破坏性变更需消费方确认 |
| P0 关键路径 E2E 全通过 | P0 清单全覆盖且全绿 | 慢轨 | 数量控制在 10–30 条（经验区间） |
| 性能 P95 阈值 | 关键场景 P95 ≤ 基线的 110% | 慢轨 | 基线随版本更新，变更需评审 |
| 无新增 P0/P1 缺陷 | 关联缺陷查询结果为空 | 发布前 | 依赖缺陷系统集成 |
| flaky 隔离区为空 | 隔离区用例数 = 0 | 发布前 | 有存量时设"不得新增"过渡期 |

### 5.3 分级门禁

同一套门禁套到所有分支，结果是"要么全部绕过，要么全部变慢"。按分支与环境分级：

| 分支 / 环境 | 生效门禁 | 目标时长（经验区间） | 绕过权限 |
|---|---|---|---|
| feature 分支 | 静态检查 + 单元 | ≤ 5 min | 无（本地可跳过，推送不可） |
| 主干合并（MR） | 上者 + 接口/契约 + 受影响模块 E2E | ≤ 15 min | 技术负责人，需留痕 |
| 发布候选 | 全部门禁 + 性能 + 安全 | ≤ 45 min | 无 |
| 线上灰度 | 合成监控关键事务通过 | 持续 | 无（自动回滚） |

门禁必须写成配置并与业务代码同仓管理，否则"改阈值"会变成零成本动作：

```yaml
# gates.yml 关键片段：受 CODEOWNERS 保护，变更需平台负责人评审
gates:
  fast:                      # feature 分支
    - lint: {max_warnings: 0, baseline: ci/lint-baseline.txt}
    - unit: {pass_rate: 1.0, skip_requires_ticket: true}
  release:                   # 发布候选
    - e2e_p0: {suite: "@p0", pass_rate: 1.0}
    - perf: {scenario: checkout, p95_ms: 800, tolerance: "baseline*1.1"}
```

## 6. 门禁反被绕过的 5 种情形

| 情形 | 观察到的现象 | 对策 |
|---|---|---|
| **门禁太慢** | 开发者本地跑一遍就推送，跳过 CI 等待 | 快轨压到 5 分钟内；慢轨异步但要能"事后追责到人" |
| **skip 泛滥** | 红灯出现后第一反应是加 `@skip` | skip 必须带工单号与到期日；skip 数进周报 |
| **只看新增失败** | 存量红灯长期存在，团队视而不见 | 基线冻结 + 只拦新增；存量单独立项清偿 |
| **改阈值而非改代码** | 性能门禁阈值被临时调高 | 阈值文件纳入 CODEOWNERS，变更需评审 |
| **权限过大** | 任何人有权限改流水线配置 | 门禁配置与业务代码分离，只允许平台负责人改 |

判断是否在被绕过，不看有没有绕过记录，看**红灯后到变绿之间的动作序列**：如果高频出现"重跑 → 通过"，说明门禁在心理上已经被绕过（对应 [10 §D4](10-anti-patterns.md)）。

留痕机制要自动生成，不能靠人举报：

| 绕过方式 | 应留痕的信息 | 谁看得见 |
|---|---|---|
| 跳过门禁 | 操作人、原因、关联工单、恢复时间 | 团队周会看板 |
| 调整阈值 | 旧值 / 新值、评审链接 | 季度复盘 |
| 手工重跑至绿 | 重跑次数、最终结果 | 周报统计 |
| 长期 skip | 工单号、到期日、责任人 | 巡检清单 |

## 7. 看板与节奏

看板不是把所有指标堆在一页，而是**每个节奏只看该节奏能决策的东西**。

| 节奏 | 看什么 | 必须回答的问题 | 参与人 | 时长 |
|---|---|---|---|---|
| **日** | 流水线红灯、阻塞中的 MR | 今天有什么在挡住合并？谁在处理？ | 值班 + 相关开发者 | 10 min |
| **周** | flaky 率、重跑率、门禁绕过次数 | 本周新增的 flaky 是哪几条，谁认领？ | 工程团队 | 30 min |
| **月** | 逃逸缺陷复盘、用例维护成本 | 上月逃逸的缺陷，哪一层本该拦住？ | QA + 开发负责人 + 产品 | 60 min |
| **季** | 成熟度评估、ROI 复核、下一季投入 | 继续投入的边际收益还在吗？ | 管理者 + 架构师 | 半日 |

**逃逸缺陷复盘是唯一必须逐条做的**：每条逃逸缺陷都要回答"该在哪一层拦住 → 为什么没拦住 → 补什么"。不产出动作的复盘会在第三次之后没人参加。

看板按受众拆成三块，而不是做一页大屏：

```
看板 A（管理层）：逃逸缺陷率、变更失败率、MTTR —— 只有趋势线，不下钻
看板 B（工程团队）：flaky 率、重跑率、快轨 P95、隔离区清单 —— 可下钻到具体用例
看板 C（平台/DevOps）：执行机利用率、排队时长、失败原因分布 —— 用于容量与稳定性
```

## 8. 度量到决策的映射

指标异常本身不是问题，**没有对应动作才是问题**。下表用于把异常直接转成待办：

| 指标异常 | 最可能的原因 | 首选动作 | 不要做 |
|---|---|---|---|
| 逃逸缺陷率上升 | 关键路径覆盖不足或断言无力 | 重画 P0 路径清单，补断言与变异测试 | 立刻加 E2E 数量 |
| 变更失败率上升 | 变更粒度大、门禁被绕过 | 缩小变更批次，恢复门禁阻断 | 增加手工回归轮次 |
| flaky 率 > 2% | 时序、数据共享、外部依赖 | 按 [07 §9](07-engineering-and-ci.md) 分类治理，进隔离区限期修复 | 全局开启自动重跑 |
| 快轨 > 10 min | 慢用例混入快轨 | 按层拆分，慢用例下沉慢轨 | 提高超时阈值 |
| 用例维护成本上升 | 用例与被测实现耦合 | 上移断言层次（UI → 接口），减少选择器依赖 | 停止写新用例 |
| 覆盖率高但逃逸率高 | 测的不是用户真实路径 | 用生产流量对比关键路径清单 | 继续提高覆盖率目标 |
| P0 缺陷带病发布 | 发布门禁缺失或可被绕过 | 门禁配置与业务代码分离，收权限 | 增加评审会 |
