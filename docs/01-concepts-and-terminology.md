## 1. 测试的本质，与自动化究竟替代了什么

一次测试由四个动作构成：

```
① 准备（Setup） → ② 执行（Act） → ③ 判定（Assert） → ④ 清理（Teardown）
```

**自动化替代的不是"人"，而是③"判定"和①④"准备/清理"。** ②"执行"本来就可以由人完成。

这个区分带来三个直接推论，是全套方法论的根：

| 推论 | 含义 | 实践后果 |
|---|---|---|
| **判定不确定，自动化无意义** | 如果连"什么算对"都说不清（审美、体验、文案是否好听），机器无法判定，只能由人做 | 探索性测试、可用性测试不应被"自动化率"指标绑架 |
| **自动化收益来自重复** | 一个只执行一次的验证，自动化成本几乎必然是负收益 | 一次性活动、临时数据核查，手工更划算 |
| **自动化的主要成本在维护，不在编写** | 编写一次性投入，维护是长期成本；环境、数据、UI 变更都会持续索费 | 选型必须评估"变更频率"，而非只看"上手快不快" |

结论：**自动化是一门投资决策，不是技术品味问题。** 后续 [02 决策模型](02-when-to-automate.md) 把这个判断做成可计算的流程。

## 2. 测试分层模型

分层不是教条，而是**成本与信心的分布图**：越底层越快、越稳、越容易定位，但离用户越远；越上层越接近真实业务价值，但越慢、越脆、越贵。

| 层级 | 验证对象 | 典型工具 | 单例耗时 | 稳定性 | 定位精度 | 建议占比（接口型系统） |
|---|---|---|---|---|---|---|
| **L1 单元** | 函数/类/纯逻辑、算法、边界、异常分支 | pytest、JUnit、Jest、Vitest、Go test、xUnit | 毫秒级 | 极高 | 精确到行 | 50%–70% |
| **L2 组件** | 单个服务的内部集成（handler + DB + 缓存） | pytest + testcontainers、Spring Boot Test、WireMock | 百毫秒级 | 高 | 到模块 | 15%–25% |
| **L3 接口 / 契约** | 服务对外 API 行为、错误码、鉴权、幂等、契约兼容性 | httpx/pytest、REST Assured、Supertest、Karate、Pact | 百毫秒–秒级 | 高 | 到接口/字段 | 10%–20% |
| **L4 端到端（E2E）** | 核心用户旅程（登录→下单→支付） | Playwright、Cypress、Selenium、Appium | 秒–分钟级 | 中 | 到步骤 | 5%–10% |
| **L5 非功能** | 性能、容量、稳定性、安全、兼容性 | k6、JMeter、Locust、Gatling、OWASP ZAP | 分钟–小时级 | 中 | 到指标 | 按需 |

> **两个必须知道的偏差**
> - **占比不是目标**。占比用来发现"我们在哪一层超配了"。团队全员在写 UI 脚本（L4 占 60%），通常意味着 L3 缺口，而不是"测试很充分"。
> - **成本随层级指数上升**：一个 L1 用例的 5 年总成本约等于 L4 用例的 1/10 ~ 1/20。所以**能在 L1 证明的问题，绝不上 L4 证明**。

### 2.1 分层决策的正确问法

不要问"要写几层测试"，要问：**"这个风险，能在哪一层被证明？"**

```
这行代码的算术/分支写错了？            → L1 单元测试
这个接口对不合法的输入会返回什么？      → L2/L3 接口测试
A 服务改字段会不会打挂 B 服务？        → L3 契约测试
用户能不能真的完成下单？               → L4 少量 E2E
一万并发下响应会不会雪崩？             → L5 性能测试
```

## 3. 测试框架（Test Framework）

### 3.1 定义

> **测试框架**：安装在项目内、由代码驱动、在同一进程（或同机）内完成"组织用例—执行—断言—报告"的工具库。它与被测代码共享版本管理，属于**开发者工具**。

关键词：**库、进程内、随仓库走、零运维、写代码使用**。

### 3.2 能力模型

一个成熟的框架通常覆盖以下能力，缺哪项就要靠胶水代码补，胶水越多越难维护：

| 能力 | 说明 | 缺失后果 |
|---|---|---|
| 用例组织与发现 | 约定命名/装饰器/标签，自动收集 | 手工维护用例清单，遗漏 |
| 断言与差异输出 | 失败时给出"期望 vs 实际"的可读差异 | 排障靠打印，效率骤降 |
| 生命周期钩子 | setup/teardown、fixture、作用域管理 | 用例间相互污染，出现"单跑通过、全跑失败" |
| 运行器 | 选择、并发、重试、超时、随机序 | 无法快速回归，无法定位顺序依赖 |
| 测试替身 | mock / stub / fake / 内存依赖 | 被迫依赖真实第三方，慢且不稳定 |
| 报告输出 | 控制台、JUnit XML、HTML、覆盖率 | CI 无法聚合，无法做门禁 |
| 参数化 / 数据驱动 | 一份逻辑 × 多组数据 | 用例爆炸式复制 |

### 3.3 形态特征（用于和平台区分）

```python
# 框架的典型使用方式：它就是项目里的一个 import
import pytest

@pytest.mark.parametrize("amount,expected", [(100, 90), (0, 0)])
def test_discount(amount, expected):
    assert apply_discount(amount) == expected
```

- 运行方式：`pytest`、`npx playwright test`、`go test ./...`
- 产物：控制台输出 + 报告文件
- 生命周期：`pip uninstall` 后就彻底消失，不留任何痕迹
- 故障影响：**只影响本仓库**

### 3.4 分类速览（详见 [03](03-test-frameworks.md)）

| 类别 | 代表 | 一句话定位 |
|---|---|---|
| 单元 / 通用 | pytest、JUnit 5、Jest、Vitest、Go test、RSpec | 主力层，量最大 |
| 接口 | httpx + pytest、REST Assured、Supertest、Karate | 企业性价比最高的一层 |
| UI / E2E | Playwright、Cypress、Selenium、Appium | 少量覆盖核心旅程 |
| 性能 | k6、JMeter、Locust、Gatling | 阈值门禁而非报告装饰 |
| 契约 | Pact、Spring Cloud Contract、schemathesis | 微服务解耦的关键 |
| 属性 / 变异 | Hypothesis、fast-check、PIT、mutmut | 验证"测试本身够不够狠" |

## 4. 测试平台（Test Platform）

### 4.1 定义

> **测试平台**：独立部署的服务系统，通过 Web 界面 + 服务端 + 执行机（agent）池 + 数据库，把测试活动作为**组织资产**进行集中管理、调度、执行与治理。

关键词：**服务、跨机器、独立运维、点界面使用、组织级**。

### 4.2 能力模型

平台的能力可以分为"必须"与"加分"两档。**采购/自建时按这张表逐项打勾，是最有效的防忽悠手段**（完整版见 [11 §平台需求清单](11-templates-and-checklists.md)）。

| 能力域 | 具体能力 | 档位 |
|---|---|---|
| 资产管理 | 用例/脚本集中存储、目录、标签、版本、跨项目复用 | 必须 |
| 调度执行 | 定时、按需、API 触发、分布式分片、并发控制、失败重试 | 必须 |
| 环境与设备 | 多环境配置、真机/浏览器矩阵、环境隔离与回收 | 必须（有矩阵需求时） |
| 结果与报告 | 聚合报告、历史趋势、失败归因、日志/录屏/trace 归集 | 必须 |
| 质量门禁 | 通过率阈值、阻断规则、与发布流程联动 | 必须 |
| 权限与审计 | 角色权限、操作留痕、合规导出 | 视合规要求 |
| 流程集成 | 需求—用例—缺陷—发布 双向追踪、CI/CD 对接 | 加分 |
| 低代码 | 非开发者可编写/维护用例、可视化编排 | 加分（有业务方参与时变为必须） |
| 数据管理 | 测试数据构造、脱敏、回收、数据集版本 | 加分（高频踩坑点） |

### 4.3 形态特征

- 部署：K8s / 虚机，需要有人负责升级、备份、容量
- 使用：浏览器打开 → 选用例 → 选环境 → 点执行 → 看报告
- 生命周期：一次引入通常运行 3–5 年，**换平台成本远高于换框架**
- 故障影响：**全团队当天无法执行测试**，直接影响发版

### 4.4 分类速览（详见 [04](04-test-platforms.md)）

| 类型 | 定位 | 代表 |
|---|---|---|
| 用例管理型 | 管理用例资产与追溯，不负责执行 | TestRail、Zephyr、禅道/PingCode 测试模块 |
| 执行/全栈型 | 管理 + 执行 + 报告一体，常内嵌框架 | Katalon、MeterSphere、自研平台 |
| 设备与浏览器云 | 提供真机/浏览器矩阵与并行执行 | BrowserStack、Sauce Labs、云真机 |
| 流水线与报告层 | 编排流程、聚合报告（**不是完整测试平台**） | Jenkins、GitLab CI、Allure |
| 可观测/合成监控 | 线上拨测与合成事务监控 | Datadog Synthetics、Grafana Synthetic Monitoring |

## 5. 测试框架 vs 测试平台：核心区别

| 维度 | 测试框架 | 测试平台 |
|---|---|---|
| **形态** | 代码库 / 包 / CLI | 独立服务系统（Web + 服务端 + 执行机） |
| **使用者** | 开发、自动化工程师（写代码） | 全团队：QA、业务、管理者（点界面） |
| **回答的问题** | "这个验证怎么写、怎么跑" | "谁在什么环境跑了哪些、结果如何、能否放行" |
| **作用边界** | 单进程 / 单机 | 跨机器、跨环境、跨团队、跨项目 |
| **扩展方式** | 写代码、装插件 | 配置、接入、调 API、编排流程 |
| **失败影响面** | 本仓库的构建 | 全组织当天的测试与发版 |
| **运维成本** | ≈ 0（`pip install` 即用） | 部署、升级、备份、容量、值班 |
| **替换成本** | 低（重写用例即可） | 高（迁移资产、流程、习惯） |
| **生命周期** | 跟仓库分支共存 | 长期运行的基础设施 |
| **典型代表** | pytest、Playwright、k6、JUnit | TestRail、MeterSphere、BrowserStack、自研平台 |

### 5.1 关系：分层，不是替代

```
┌──────────────────────────────────────────────┐
│  测试平台      调度 / 环境池 / 报告 / 门禁 / 审计   │  ← 组织层：治理与协同
├──────────────────────────────────────────────┤
│  CI 流水线     触发 / 分片 / 阻断 / 制品归档        │  ← 流程层：自动化执行编排
├──────────────────────────────────────────────┤
│  测试框架      用例本体 / 断言 / 替身 / 报告文件     │  ← 表达层：测试逻辑
├──────────────────────────────────────────────┤
│  被测系统                                          │
└──────────────────────────────────────────────┘
```

**关键结论：平台底层仍然调用框架。** 平台的执行机上跑的还是 `pytest`、`npx playwright test`。因此：

> 没有用例资产的平台 = 空壳。这是自建平台与采购平台失败的头号原因（见 [10 §P1](10-anti-patterns.md)）。

**类比**：框架是锤子和锯子，平台是车间。车间里也放着锤子，但车间的价值在工位、排产、质检和台账，而不在于"更高级的锤子"。

### 5.2 半平台地带（最容易吵不清的部分）

现实中的工具有很多"越界"，判断标准是**它是否需要独立部署、是否跨仓库/跨团队管理资产**：

| 工具 | 实际定位 | 越界的那一半 |
|---|---|---|
| Playwright | 框架（但自带 runner、并行分片、HTML 报告、trace viewer） | 已有"半平台"能力，多团队独用时仍感不足 |
| Allure | 报告层 | 只做可视化聚合，既不是框架也不是平台 |
| Jenkins / GitLab CI | 流水线平台 | 注意：**它不是测试平台**，不替你管理用例资产 |
| TestRail | 用例管理层 | 注意：**它不执行**，执行要靠 CI/框架回写结果 |
| Katalon / MeterSphere | 全栈平台 | 内嵌自研框架，框架不可脱离平台使用（锁定风险） |
| DVC/数据集 + pytest | 数据层 + 框架 | 补齐"测试数据治理"这一常被忽略的能力 |

## 6. 五个高频混淆（面试与方案评审必问）

1. **"Jenkins 就是我们的测试平台吧？"**
   —— 不是。Jenkins 负责"触发与编排"，不负责用例资产、环境池、结果趋势、质量门禁策略。它可以作为平台的执行后端。
2. **"我们买了 TestRail，平台就齐了？"**
   —— 只补齐了"资产管理"一格。执行、调度、环境池、门禁仍缺，需要 CI 或自研补齐。
3. **"Playwright 能并行、有报告，所以不需要平台。"**
   —— 单团队单仓库成立。当出现多项目共享、设备矩阵、统一门禁、非开发者参与时，它的半平台能力会到顶。
4. **"覆盖率 80% = 质量好。"**
   —— 覆盖率只说明"代码被执行过"，不说明断言有效。需要变异测试（mutation testing）验证断言的杀伤力，见 [03 §8](03-test-frameworks.md)。
5. **"上平台就能提升测试效率。"**
   —— 平台提升的是**组织协同效率**，不是单条用例的质量。用例写得不好，上平台只是让低质量用例跑得更快、更显眼。

## 7. 术语表

| 术语 | 定义 | 易混淆点 |
|---|---|---|
| **用例资产（Test Asset）** | 可被复用、被维护、被度量的测试代码/数据/配置的集合 | 与"测试用例文档"不同，强调可执行性与维护责任 |
| **判定标准（Oracle）** | 判断"实际结果是否正确"的依据 | 无 oracle 的测试不是测试，只是脚本 |
| **测试替身（Test Double）** | 替代真实依赖的假实现：stub / mock / fake / spy / dummy | mock 验证交互，stub 提供数据，fake 是轻量真实现 |
| **契约测试（Contract Test）** | 验证服务间接口约定是否兼容，通常由消费方定义 | 不等于接口测试；契约测试关注"兼容性" |
| **测试金字塔** | L1 多、L4 少的投资结构 | 反模式是"冰淇淋筒"（UI 最多） |
| **测试分片（Sharding）** | 把用例集切分到多台执行机并行 | 与"并发执行"相关但不同：分片是切分，并发是同时跑 |
| **flaky 用例** | 同样代码、同样环境，结果不稳定的用例 | 根因多为时序、数据共享、外部依赖、随机序 |
| **逃逸缺陷（Escaped Defect）** | 测试未拦住、流入生产或被用户发现的缺陷 | 比"用例数"更能反映测试有效性 |
| **门禁（Quality Gate）** | 不满足条件即阻断流水线/发版的规则 | 门禁要少而硬，多而软等于没有 |
| **合成监控（Synthetic Monitoring）** | 用脚本在线上主动拨测核心链路 | 属"测试右移"，与平台共用用例资产 |
| **测试左移 / 右移** | 把质量活动提前到设计编码阶段 / 延伸到生产环境 | 左移不是"让开发多写测试"这么简单 |
| **变异测试（Mutation Testing）** | 故意在代码里注入错误，检验测试能否发现 | 衡量"断言杀伤力"，不是覆盖率 |
| **特性测试（Property-based）** | 声明不变量，由框架生成大量输入 | 擅长发现边界与罕见组合 |
| **测试数据工厂（Data Factory）** | 按需构造合法/非法测试数据的组件 | 与"固定数据集"相比更适合同隔离 |
| **环境即代码（Environment as Code）** | 用容器/脚本声明式创建测试环境 | testcontainers 是其典型实现 |
| **TCO（总拥有成本）** | 采购/自建 + 运维 + 迁移 + 培训 + 机会成本 | 选型时最易被低估的一项，见 [05 §4](05-selection-methodology.md) |
| **ADR（架构决策记录）** | 记录"为什么这么选"的短文档 | 选型结论必须留 ADR，见 [11 §5](11-templates-and-checklists.md) |
