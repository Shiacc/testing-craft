# 12 · 真实项目接入实战

> **适用读者**：要把自动化测试落到一个**真实项目**上的工程师、QA 负责人　|　**前置阅读**：[02](02-when-to-automate.md)、[07](07-engineering-and-ci.md)
>
> 本文记录一次真实接入：把一个**开源全栈项目**跑起来，在它上面建成 L1→L4 四层测试，
> 再接到用例库与缺陷系统。所有数字都来自 `labs/07-real-project` 的实测。

---

## 1. 为什么必须用真实项目

自己造的被测系统会**不自觉地配合测试**：字段刚好稳定、错误刚好可断言、状态机刚好简单。
真实项目才会暴露真正让人卡住的地方——本实验第一轮就撞了四个：

| 撞到的问题 | 现象 | 处理 |
|---|---|---|
| 后台按钮藏在折叠菜单里 | `click` 超时 30s，元素"存在但不可见" | `get_by_role(...).click()` 打开 "More actions" → `expect(publish).to_be_visible()` → 再点 |
| slug 由前端 blur 时生成 | 直接提交 → "slug 不能为空" 校验失败 | 填标题 → `blur()` → 等 `#id_slug` 非空 → 再提交 |
| 页面 URL 由父页面决定 | 写死 `/guide/xxx/` 会随种子变化失效 | 种子落盘 `.seed_state.json`，用例读父页面 ID |
| 服务端模板缺 `{% load %}` | 所有内容页 500，错误藏在 HTML 里 | 用 `Django test client` 复现（比读浏览器报错快） |

> 这四条都不是"测试技巧"，而是**真实系统的形状**。造一个玩具项目，你会永远学不到它们。

## 2. 选型：什么样的开源项目适合做"接入演练"

| 标准 | 理由 | Wagtail（本次选择） |
|---|---|---|
| 真实业务流 | 能覆盖"创建→发布→可见"这类跨层流程 | ✅ 内容管理：建页→发布→前台渲染 |
| 前后端都有 | 需要同时练 L3 与 L4 | ✅ Django 服务端渲染 + 后台 SPA |
| 能在 10 分钟内跑起来 | 否则演练会变成环境折腾 | ✅ `pip install wagtail` + `migrate` |
| 不强制 Node 构建 | 减少工具链不确定性 | ✅ 后台静态资源随包分发 |
| 有管理后台 | 真实项目的主要交互面在后台 | ✅ Wagtail admin |
| 社区活跃、可查文档 | 遇到问题能搜到答案 | ✅ 20k+ star |

**被否掉的候选**：`django-oscar`（更强电商语义，但 sandbox 需要 clone 整个仓库并装大量依赖，
本次网络条件下 clone 超时）；纯 API 项目（没有 L4 可练）；需要 Node 构建的前端为主项目（本机无 Node）。

## 3. 接入七步（可照抄）

```
① 选型           按 §2 的六条标准筛；写进 README 说明"为什么不选另一个"
② 隔离环境       独立目录、独立数据库（sqlite）、固定端口、独立账号；绝不连共享环境
③ 最小改动       只加"便于隔离与观测"的东西：一个内容页模型、一个种子命令、一个清理命令
④ 种子数据       幂等创建 + 落盘 ID（.seed_state.json），让断言有稳定锚点
⑤ 探活前置       conftest 里先探站点可达，不可达直接 exit(3) 并给出启动命令
⑥ 分层用例       先 L3 再 L4，L4 只保留"跨层才需要"的 2 条
⑦ 数据清理       qa- 前缀 + 管理命令 + session 前后自动清理
```

### ② 隔离环境的具体做法

| 维度 | 做法 | 不这么做的后果 |
|---|---|---|
| 端口 | 固定 `127.0.0.1:8099`，脚本里写死并文档化 | 与开发环境抢端口，随机失败 |
| 数据库 | 项目自带 sqlite，删掉即重置 | 连共享库 → 测试数据污染真实业务 |
| 账号 | `qa / qa-pass-12345`，由管理命令幂等创建 | 手工建号 → 换机器就跑不了 |
| 凭据 | 环境变量注入，`.env` 不入库 | 密码进 Git 历史，只能靠改密补救 |

### ④ 种子数据为什么要落盘 ID

Wagtail 的"新建页面"URL 是 `/admin/pages/add/<type>/<parent_id>/`，父页面 ID 每次重建都不同。
把 ID 写死在测试里 → 重建库就全红；去后台点着找 → 脆弱且慢。
落盘一份 `.seed_state.json`（只含 ID 与 slug，不含凭据）是最小代价的解法：

```json
{"home_id": 3, "pages": {"about": 4, "guide": 5},
 "children": {"guide": {"first-page": 6, "publishing": 7, "search": 8}}}
```

## 4. 本实验的四层用例（实测）

| 层 | 文件 | 断言什么 | 数量 | 耗时 |
|---|---|---|---|---|
| L1 | `test_l1_seed_plan.py` | 种子计划结构：slug 唯一、标题/摘要非空 | 3 | < 0.1s |
| L3 | `test_l3_site_http.py` | 页面 200、主标题、子链接、sitemap、静态资源、后台登录页 | 7 | ~1s |
| L4 | `test_l4_admin_ui.py` | 后台登录；新建→发布→前台可见 | 2 | ~8s |
| 计 | | | **13 + 1（canary）** | **8.2s** |

**L1 测的是"我们自己的胶水代码"**（种子计划、路径、校验），不是 Wagtail 内部逻辑。
框架自身逻辑由上游测试保证，重复覆盖它既慢又无价值——这是 [02 §6](02-when-to-automate.md)
"在能证明问题的最底层断言"的具体应用。

### L4 为什么只有 2 条

| 用例 | 为什么值得占 E2E 预算 |
|---|---|
| 管理员可登录后台 | 认证坏了 → 全部后台功能不可用，P0 |
| 新建页面→发布→前台可见 | 跨 UI + 权限 + 数据库 + 发布状态机 + 前台渲染五层，只有 E2E 能证明 |

其余（字段校验、列表分页、搜索排序）都应在 L3 或更低层断言。

## 5. 五个真实坑与修法

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | 元素存在但不可见 | `click` 超时 30s | 先展开容器（`More actions`），再 `expect(button).to_be_visible()` |
| 2 | 前端副作用（slug）未就绪 | 提交后校验失败 | blur 触发 + 断言 `#id_slug` 非空 |
| 3 | 成功判据用 URL | 发布后跳到哪一页不稳定 | 用**页面上的成功提示**（`created and published`） |
| 4 | 失败时看不到现场 | 只看到 AssertionError | `--junitxml` + 控制台日志归档 + 失败截图（本实验在 conftest 预留钩子） |
| 5 | 测试数据残留 | 第二次跑 slug 冲突 | `qa-` 前缀 + 会话前后清理命令 |

> 第 3 条最值得记住：**URL 不是契约，用户看到的消息才是**。

## 6. 验收清单（接入完成的标准）

- [x] `bootstrap.ps1` 一条命令从零到可跑（幂等，重复执行不报错）
- [x] 站点不可达时测试给出明确指引（而不是 13 条红色 traceback）
- [x] 每条用例都能追到用例库 ID（`atf validate` 0 error）
- [x] 执行结果回写用例库（`last_run` / `last_result` 有值）
- [x] 失败可生成缺陷草稿（`atf file-bugs --dry-run`）
- [x] 跑完无残留（`cleanup_qa_pages` 输出"没有需要清理的测试页面"）
- [x] 全部用例 8 秒内跑完（本地）
