# 03 · 测试框架全景

>
> 本文只讨论**测试框架**——进程内、随仓库走、零运维的代码库。平台选型见 [04](04-test-platforms.md)，加权评分流程见 [05](05-selection-methodology.md)。文中耗时、成本、比例为**业界经验区间**，用于建立数量级直觉，落地时必须用自身历史数据替换。

## 1. 阅读视角：框架选型真正该看的 5 个维度

结论先行：**框架选型不是"哪个最强"，而是"哪个在你这支队伍、这条流水线、这三年里总成本最低"。**

| # | 维度 | 要回答的问题 | 不合格的表现 | 经验权重 |
|---|---|---|---|---|
| 1 | 能力覆盖 | 我们要验的风险，它原生能不能验？ | 三项核心能力里两项靠自制胶水 | 25% |
| 2 | 生态与人才 | 招得到人吗？遇到问题搜得到答案吗？ | 全公司只有 1 人会，社区周提问 < 5 条 | 20% |
| 3 | CI 兼容 | 能否无头运行、产出 JUnit XML、支持分片与超时？ | 必须开 GUI，报告只有截图 | 25% |
| 4 | 锁定风险 | 用例能否脱离某个商业服务独立运行？ | 脚本存在厂商云端，导出即失效 | 15% |
| 5 | 迁移成本 | 换掉它要重写多少、要多久？ | 断言与用例结构全绑在私有 DSL 上 | 15% |

三条使用说明：

- 权重是**经验区间**，进入 [05 选型方法论](05-selection-methodology.md) 的加权矩阵前必须按场景重设。
- 维度 3 是**一票否决项**：进不了 CI 的框架，在企业里等于不存在。
- 维度 4、5 只在"要长期维护 500 条以上用例"时才真正开始计费；小规模阶段可以先用后算。

## 2. 单元 / 通用框架

单元层量最大、成本最低、定位最准，是唯一"多写不亏"的一层。以下 6 个框架覆盖企业里 95% 的单元测试场景。

### 2.1 能力对比

| 框架 | 语言 | 断言 | 参数化 | fixture / 生命周期 | 并发 | 插件生态 | 报告 |
|---|---|---|---|---|---|---|---|
| **pytest** | Python | 原生 `assert`（断言重写，失败给差异） | `@parametrize` + 数据文件 | fixture 作用域 function/class/module/session，依赖注入 | pytest-xdist 进程级 | 极强（千级插件） | JUnit XML、pytest-html、Allure |
| **JUnit 5** | Java / Kotlin | AssertJ / Hamcrest 生态 | `@ParameterizedTest` + `@MethodSource` | `@BeforeEach`、`@Nested`、Extension 模型 | Platform 并行（配置开关） | 强（Surefire / Gradle 原生） | Surefire XML、HTML |
| **Jest** | JS / TS | `expect` + 快照 | `test.each` | `before*/after*` + setup 文件 | worker 进程池 | 强（jsdom、msw 生态） | 控制台、jest-junit |
| **Vitest** | JS / TS | `expect`（Jest 兼容） | `test.each` | `test.extend` fixture + 钩子 | worker 线程池 + 分片 | 强且现代（Vite 生态） | JUnit、HTML、v8 覆盖率 |
| **Go test** | Go | 原生 `if` + `t.Error`（无内置断言库） | 表驱动 + `t.Run` 子测试 | `TestMain`、`t.Cleanup` | `t.Parallel()`（goroutine） | 弱（标准库优先） | `-json`、gotestsum |
| **RSpec** | Ruby | `expect(...).to eq` | 共享示例 + 循环 | `before`、`let`、`subject` | parallel_tests gem | 中（gem 成熟但小众） | JUnit formatter、HTML |
| **TestNG** | Java | Assert / AssertJ | `@DataProvider` | `@BeforeSuite`、`@BeforeGroups` | `parallel="methods/tests"` 原生 | 中（Selenium 时代遗产） | TestNG XML / HTML |

### 2.2 各自适用要点

| 框架 | 最适配 | 明确不适合 |
|---|---|---|
| pytest | 数据 / 算法 / 接口混合栈；需要最多插件与最省力的报告改造 | 强类型约束下的大型多人协作（要靠 mypy / pydantic 补） |
| JUnit 5 | JVM 单体或微服务，与 Spring Boot Test 同栈 | 团队无 JVM 经验时，启动成本高于收益 |
| Jest | 前端组件、存量 CRA / Next 项目、需要快照 | 大型 TS monorepo（ESM 转译链易碎，配置成本高） |
| Vitest | Vite / Vue / React 新项目，TS 优先 | 深度依赖 Jest 专有生态的存量项目 |
| Go test | Go 服务端、CLI、并发逻辑 | 需要丰富 mock 与报告生态的复杂场景（需自建） |
| RSpec | Ruby / Rails | 非 Ruby 团队（人才池窄，交接风险高） |
| TestNG | 存量 Selenium 套件、需要 XML 编排分组 | 新项目（活跃度低于 JUnit 5） |

### 2.3 三个高频坑

| 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|
| **fixture 作用域污染** | "单跑通过、全跑失败"；换执行顺序结果就变 | session 级 fixture 持有可变状态或共享数据库连接 | 默认 function 作用域；跨用例共享只放只读数据；写操作一律 function 级 + 事务回滚 |
| **mock 过度** | 改实现就挂 30 个用例，业务行为其实没变 | 对内部协作对象逐个 mock，测试退化为"实现快照" | 只 mock 进程外边界（HTTP、时钟、随机、队列）；内部协作改用 fake 或真对象 |
| **断言过弱** | 覆盖率 80%，线上仍出低级错 | 只断言状态码或"非空"，不断言业务字段与副作用 | 每用例至少一条业务语义断言；用变异测试抽检（§7） |

断言强弱的具体差别：

```python
# 弱断言：只要不报错就算过
assert resp.status_code == 200

# 有效断言：锁定契约与副作用
assert resp.json()["order"]["status"] == "PAID"
assert resp.json()["order"]["amount"] == 9900   # 以分为单位，防精度回归
assert ledger.count(order_id) == 1              # 副作用只发生一次
```

## 3. 接口测试框架

结论：**接口层是企业自动化性价比最高的一层**——比 UI 快 1–2 个数量级（经验区间），比单元更贴近对外契约，同等覆盖下维护成本约为 UI 用例的 1/5（经验区间）。

为什么是"最高性价比"：

| 优势 | 具体表现 |
|---|---|
| 快 | 单例百毫秒级，千条用例可在 10 分钟内跑完（经验区间） |
| 稳 | 不依赖渲染、不依赖设备，flaky 率显著低于 UI |
| 定位准 | 失败直接指向接口与字段，不需要"猜是前端还是后端" |
| 复用广 | 同一套用例可被 CI、合成监控、压测脚本复用 |
| 前置条件少 | 只要服务可访问 + 一份测试数据 |

### 3.1 能力对比

| 框架 | 语言 / DSL | 断言风格 | schema / 契约校验 | 运行依赖 | 上手成本 |
|---|---|---|---|---|---|
| **httpx + pytest** | Python 代码 | 原生 assert + 自定义校验器 | 可接 jsonschema / pydantic | 纯 Python，无额外服务 | 低 |
| **REST Assured** | Java DSL `given/when/then` | Hamcrest 匹配器 | 内置 JSON Schema 校验 | JVM + 测试框架 | 中 |
| **Supertest** | Node.js 代码 | expect / assert 库 | 需外接 ajv | 与被测 app 同进程（可不起服务） | 低 |
| **Karate** | Gherkin 风格 DSL | 内建 `match`（含模糊匹配） | 内建 schema / contains | JVM，自带 runner | 中（DSL 需专门学） |
| **Schemathesis** | Python，基于 OpenAPI / GraphQL | 属性断言（响应符合 schema） | 以 schema 为唯一来源 | 需可用的 schema | 低（但依赖 schema 治理） |

### 3.2 用例矩阵（接口层的最小完整集）

只写"正常路径"的接口测试，等于只验证了系统最不会出问题的那条路。**六类用例缺一不可：**

| 用例类型 | 设计要点 | 必断言内容 | 最易遗漏 |
|---|---|---|---|
| **正常路径** | 每接口 1–2 条，覆盖主业务分支 | 状态码 + 业务字段 + 关键副作用 | 副作用（消息投递、库存扣减、账务流水） |
| **边界** | 数值 0 / 负数 / 上限、字符串长度上限、时间跨天与闰秒、分页最后一页 | 边界值被接受或被拒绝的确切行为 | 金额精度（分 vs 元）、空列表与 null 的区别 |
| **非法输入** | 缺字段、类型错、超长、注入字符、非法枚举 | 4xx 且错误码稳定，绝不出现 500 | 错误码随版本漂移，断言写死魔法字符串 |
| **鉴权 / 越权** | 无 token、过期 token、他人资源 ID、角色不足 | 401 与 403 区分清晰，不泄露资源是否存在 | 水平越权（IDOR）：用别人 ID 能读到数据 |
| **幂等** | 同一幂等键重复提交 | 结果一致，副作用只发生一次 | 只测"第二次也返回 200"，没查副作用次数 |
| **幂等重放** | 并发重放、超时后客户端重试、跨节点重放 | 唯一约束生效，无重复扣款 / 重复发货 | 并发窗口（两个请求同时到达） |

### 3.3 设计要点

- **用例即数据**：请求体与期望值放参数化表，禁止为每组数据复制函数。
- **一个断言主题**：一条用例只证明一件事，失败信息能直接定位到原因。
- **认证只做一次**：session 级 token fixture，避免每例登录拖慢整体。
- **数据自造自清**：唯一前缀 + teardown 删除，禁止依赖固定 ID 与固定账号。
- **错误码表进仓库**：把错误码收敛到 `errors.yaml` 等单一来源，断言引用它而非硬编码。
- **定义即事实**：先由 OpenAPI 生成请求骨架，再补业务断言；schema 与用例同仓同评审。

最小片段（结构示意，完整版见 [labs/](../labs/README.md)）：

```python
@pytest.mark.parametrize("case", ORDER_CASES, ids=lambda c: c.name)
def test_create_order(client, case):
    r = client.post("/v1/orders", json=case.payload, headers=auth_header())
    assert r.status_code == case.expect_status
    assert r.json()["code"] == case.expect_code
```

### 3.4 接口层的五个反模式

| 反模式 | 症状 | 修法 |
|---|---|---|
| **只测状态码** | 200 就算过，业务字段错了照样绿 | 加业务字段与副作用断言（§2.3） |
| **用例互相依赖** | 必须按 A→B→C 顺序跑，单跑必挂 | 每用例自造数据，禁止复用上一例产物 |
| **打真实第三方** | 夜间频繁失败，重跑就过 | 进程外边界一律 stub（支付、短信、对象存储） |
| **断言具体报文全文** | 后端加一个字段就挂 100 条 | 断言字段子集，其余用 schema 校验 |
| **测试环境写死** | 换环境要改代码 | baseURL 与凭据走配置/环境变量 |

这五条的共同点：**它们都不是框架能力问题，而是用例设计问题。** 换框架不会修好其中任何一条。

## 4. UI / E2E 框架

结论：**UI 层只该覆盖"跨系统、跨角色、有营收影响"的 5–10 条旅程。** 把它当主力层，维护成本会在 6 个月内失控（经验区间：同等覆盖下 UI 用例的 5 年成本是接口用例的 5–10 倍）。

### 4.1 架构性差异（不是功能清单，是架构决定的）

| 维度 | Playwright | Cypress | Selenium | Appium |
|---|---|---|---|---|
| **驱动架构** | 浏览器协议直连（CDP / WebKit），进程外控制 | 在浏览器内运行 runner，与应用同进程 | W3C WebDriver，经 driver 转发 | WebDriver 扩展（XCUITest / UiAutomator2） |
| **多标签页 / 多窗口** | 原生 context + page，可同时操作 | 不支持真正的多标签，跨域靠 `cy.origin` | 原生支持 window handle 切换 | 受限于设备与系统能力 |
| **多浏览器** | Chromium / Firefox / WebKit 一套 API | Chrome 系 + Firefox，WebKit 实验性 | 全浏览器，需匹配对应 driver | iOS / Android 真机与模拟器 |
| **语言支持** | TS/JS、Python、Java、.NET | 仅 JS / TS | Java、Python、C#、Ruby、JS | Java、Python、C#、Ruby、JS |
| **自动等待** | 内建 actionability 检查（可见、稳定、可点） | 内建 retry-ability | 无，需显式等待 | 无，需显式等待 + 设备性能差异 |
| **trace / 录屏** | trace viewer（DOM 快照 + 网络 + 源码） | 视频 + 命令日志 | 需自建（Grid + 第三方录屏） | 截图 + 设备日志 |
| **并行模型** | 内置 worker + shard，按文件切分 | 本地需自建，官方并行依赖商业云 | Selenium Grid 或云厂商 | 设备池（真机数量即并发上限） |
| **网络拦截** | `route` / `fulfill`，可改请求与响应 | `cy.intercept`，能力强 | 有限（CDP / 双向协议，跨浏览器不一致） | 无原生支持，需设备侧代理（mitmproxy） |

这张表最关键的一行是**自动等待**：它直接决定 flaky 率。UI 用例的失败里，多数是"元素还没准备好"而不是"功能坏了"。没有自动等待的框架，团队要为每条用例手写等待逻辑，而那正是 flaky 的主要来源。

### 4.2 什么情况选谁

| 你的情况 | 选择 | 理由 |
|---|---|---|
| 新项目、Web 为主、要跨浏览器与并行 | **Playwright** | 自动等待 + trace 把 flaky 定位成本压到最低 |
| 前端团队主导、只要 Chrome 系、看重调试体验 | Cypress | 时间旅行调试友好，前端接受度高 |
| 存量 Java 体系、已有 Grid、需老浏览器 | Selenium | 兼容面最广，迁移成本最低 |
| 移动端 Native / Hybrid 为主 | Appium（+ 设备云） | 目前唯一成熟的跨平台移动方案 |
| 移动端 + Web 混合 | Playwright（Web）+ Appium（Native），共用账号与数据工厂 | 不要试图用一个框架通吃两端 |

设备与浏览器矩阵的成本量级（**经验区间**）：自建 ≈ 每并发节点 1–3 万元一次性投入 + 每月 500–2000 元运维；因此设备层通常"买"比"建"划算，见 [04 §3.3](04-test-platforms.md)。

### 4.3 UI 层三条纪律

1. **选择器优先级**：`data-testid` > role / label > 文本 > CSS > XPath。绝对 XPath 是维护灾难，应直接禁止。
2. **一条旅程一个测试**：中途不写"顺手验证一下"的断言，失败时才能一眼判断是哪条业务流断了。
3. **失败必须能自证**：trace + 视频 + 网络日志三件套，缺一项就视为不可维护（排障时间会超过重写时间）。

## 5. 性能框架

结论：**性能脚本的第一产出是"阈值"，不是"报告"。** 没有阈值的压测只是表演——它产出一张没人看的图，然后被忘记。

### 5.1 能力对比

| 框架 | 脚本形态 | 协议覆盖 | 分布式 | 资源效率 | CI 友好度 | 报告 |
|---|---|---|---|---|---|---|
| **k6** | JS（ES module），代码即脚本 | HTTP/1.1、HTTP/2、WebSocket、gRPC | 开源版需 k6 operator 自建；商业版托管 | 高（Go 引擎，单机可压数千 VU） | 高（单二进制，阈值即退出码） | 终端摘要 + JSON/CSV + 商业版看板 |
| **JMeter** | XML `.jmx`（GUI 编辑） | 极广（JDBC、JMS、FTP、LDAP、MQ 等） | master/slave 原生 | 低（JVM 线程模型，内存开销大） | 中（需插件出报告，jmx 难评审） | HTML Dashboard（插件） |
| **Locust** | Python 代码 | HTTP 为主，可自写 client | master/worker 原生 | 高（gevent 协程） | 高（纯 Python，易嵌 CI） | Web UI + CSV，HTML 需插件 |
| **Gatling** | Scala / Java DSL | HTTP、WebSocket、JMS | 开源版需自建；企业版托管 | 很高（Netty 异步） | 中高（依赖构建工具，报告优秀） | 内建 HTML 报告 |

选择逻辑很短：

- 团队写 Python → **Locust**；写 JS/TS → **k6**；必须验 JDBC/JMS 等企业协议 → **JMeter**；追求极限吞吐且接受 Scala → **Gatling**。
- **只要团队里没人愿意维护 `.jmx`，就不要选 JMeter**：GUI 生成的 XML 无法 code review，是长期负债。

### 5.2 阈值当门禁，不是出个报告就完事

```javascript
// k6：阈值不达标 → 非 0 退出码 → CI 直接红
export const options = {
  thresholds: {
    http_req_duration: ['p(95)<300', 'p(99)<800'],
    http_req_failed:   ['rate<0.01'],
  },
};
```

| 指标 | 建议口径 | 阈值（**经验区间**，须用自身基线替换） | 为什么定它 |
|---|---|---|---|
| p95 延迟 | 成功请求，排除预热窗口 | < 300 ms | 用户体验拐点，且比均值抗异常值 |
| p99 延迟 | 同上 | < 800 ms | 捕捉尾部抖动，暴露锁竞争与 GC 停顿 |
| 错误率 | 5xx + 业务失败码 | < 1% | 比"平均响应时间"更早暴露容量问题 |
| 吞吐 | 目标 RPS 下的稳定值 | ≥ 峰值的 1.5 倍 | 留出突发流量与滚动发布余量 |
| 资源水位 | CPU / 连接池 / GC | CPU < 70%，连接池等待 < 5% | 找到真实瓶颈，而非只报一个数字 |

三条纪律：

- 压测必须在**固定基线环境**跑，配置与生产同比例，否则数字不可比。
- 只与上一次同场景结果对比，看趋势不看绝对值。
- 阈值写进仓库，与 [08 质量门禁](08-metrics-and-quality-gates.md) 联动，出现在发布检查单里。

### 5.3 压测场景类型（别把四种混成一种）

| 场景 | 目的 | 负载形态 | 时长（经验区间） | 进门禁吗 |
|---|---|---|---|---|
| 冒烟压测 | 验证脚本与链路可用 | 1–5 VU 恒定 | 1–2 分钟 | 是（每次发布） |
| 基准压测 | 建立性能基线 | 阶梯升到目标 RPS | 10–20 分钟 | 是（每次发布或每日） |
| 容量压测 | 找拐点与瓶颈 | 阶梯递增至错误率超标 | 30–60 分钟 | 否（按月/按版本） |
| 稳定性压测 | 找内存泄漏、连接耗尽 | 70% 容量恒定 | 2–8 小时 | 否（夜间/每周） |

最常见的错误是**只做容量压测**：一次性把系统压到崩，得到一张漂亮的曲线，然后既没有基线可对比，也没有门禁可阻断，下次发版仍然靠感觉。

## 6. 契约测试

结论：**微服务的第一大故障源是"接口变了没人知道"，契约测试是唯一能在合并前拦住它的低成本手段。** 但它不是免费的：需要 broker、需要 provider 侧配合验证、需要"谁改谁负责"的约定。

### 6.1 三种方案

| 方案 | 契约来源 | 工作方式 | 适用 | 落地成本 |
|---|---|---|---|---|
| **Pact** | 消费方测试生成 pact 文件 | 消费方定义期望 → 上传 Broker → provider 拉取并回放验证 | 多语言、消费方多的服务网格 | 中高：需 Broker（自建或云）、需管理 provider 状态 |
| **Spring Cloud Contract** | 生产方 DSL（Groovy / YAML） | 生成 stub 给消费方 + 生成 provider 侧测试 | JVM、Spring 栈、单体拆微服务 | 中：仅 JVM，需 Gradle/Maven 插件 |
| **Schemathesis** | OpenAPI / GraphQL schema | 由 schema 生成大量请求，校验响应合规 | 已有可靠 schema 的 HTTP 服务 | 低：无需 broker，但完全依赖 schema 质量 |

### 6.2 价值与成本对照

| 收益 | 量化口径（**经验区间**） | 对应成本项 |
|---|---|---|
| 提前拦截不兼容变更 | 接口类线上故障下降 30%–60% | 消费方需写契约测试，约每接口 0.5–1 人日 |
| 减少联调等待 | 联调轮次减少 1–2 轮 | Broker 运维约 0.2 人 |
| 可替代部分 E2E | 跨服务 E2E 用例可减 30%–50% | provider 验证失败需人判断"该谁改" |

判断规则：

- 服务数 < 3 且同团队维护 → **先不做契约**，接口测试 + schema 校验足够。
- 消费方 ≥ 2 或跨团队 → Pact 的收益立刻为正，因为它把"兼容性"从口头约定变成了构建结果。
- Schemathesis 只有在 schema 由 CI 强制校验（lint + 版本 diff）时才稳定出活；schema 是手写装饰品的团队会得到一堆噪音。

### 6.3 契约测试的最小落地形态

```python
# 消费方：定义"我期望对方返回什么"（片段示意）
pact.given("订单 123 已支付") \
    .upon_receiving("查询订单状态") \
    .with_request("GET", "/v1/orders/123") \
    .will_respond_with(200, body={"status": "PAID", "amount": 9900})
```

落地时必须同时回答三个问题，否则契约会变成"写了但没人验证"：

| 问题 | 不回答的后果 |
|---|---|
| provider 侧由谁执行验证？在哪个流水线？ | 契约只证明消费方的想象，未证明对方的实现 |
| 契约破坏时谁负责改？ | 双方互推，最后选择"先跳过" |
| provider 状态（provider state）怎么准备数据？ | 验证脚本自己造数据，与消费方假设不一致 |

## 7. 探索性 / 进阶技术

这四类技术解决的不是"功能对不对"，而是**"测试本身够不够狠"**。它们不该在第一天引入。

| 技术 | 代表工具 | 解决什么问题 | 何时值得引入 | 引入成本 |
|---|---|---|---|---|
| **属性测试** | Hypothesis（Python）、fast-check（JS/TS） | 手工想不到的输入组合与边界 | 存在明确不变量：金额守恒、序列化往返、排序幂等 | 低：改写 5–20 条核心用例即可试点 |
| **变异测试** | PIT（JVM）、Stryker（JS/TS/C#）、mutmut（Python） | 断言是否有杀伤力，覆盖率是否虚高 | 核心域：支付、计费、权限、状态机 | 中高：全量跑可能数小时，须用增量模式 |
| **模糊测试** | Atheris（Python）、Jazzer（JVM） | 解析器、协议、序列化层的崩溃与内存安全 | 有外部输入解析：文件、报文、图片 | 中：需语料库与崩溃去重流程 |
| **视觉回归** | Playwright `toHaveScreenshot`、Percy、BackstopJS | 样式 / 布局回归（人工看截图看不完） | 设计系统、营销页、多端适配 | 中：需基线管理 + 容差策略 |

引入顺序（按"信号强度 / 成本"排）：

```
断言有效性存疑  → 变异测试（增量，只跑改动文件）
边界遗漏频发    → 属性测试（先写 5 条不变量）
解析层崩溃      → 模糊测试（先跑夜间任务）
UI 样式回归     → 视觉回归（先 3 个核心页面，容差 0.1%）
```

一条反直觉结论：**变异测试的分数比覆盖率更能预测线上质量。** 覆盖率 80% 但变异杀伤率 40% 的代码库，其真实防护力低于覆盖率 60% 但杀伤率 75% 的代码库（经验观察，需用自身逃逸缺陷数据校准）。

## 9. 框架选型的 6 条硬规则

这 6 条不是"建议"，是**违反即会付出可预期代价**的门槛：

| # | 规则 | 可检验判据 | 违反后果 |
|---|---|---|---|
| 1 | **优先团队已有技能** | 现有成员中 ≥ 2 人能独立改脚本并 review | 单点依赖，人一走资产冻结 |
| 2 | **必须能进 CI 且产出 JUnit XML** | 无头运行 + `--junitxml` 或等价物可被流水线解析 | 无法聚合、无法做门禁，报告等于装饰 |
| 3 | **禁止只能 GUI 操作、无法版本化的工具** | 脚本与配置能 diff、能 code review | 变更不可审计，回滚靠人肉 |
| 4 | **禁止无法离线 / 内网运行的框架** | 断网环境可完整跑通一次 | 内网与隔离环境直接不可用 |
| 5 | **锁定必须可退出** | 有一套"导出 → 离线跑通"的验证过的迁移路径 | 议价权归厂商，续费被动 |
| 6 | **单一职责，不搞一栈通吃** | 每层有明确主框架，边界写进 ADR | 工具互相打架，排障成本翻倍 |

补充两条判读经验：

- 规则 2 与规则 3 合起来能筛掉 80% 的"演示很漂亮、落地很痛苦"的工具。
- 规则 5 的验证必须**在上线前做一次**，而不是等要换的时候才做——那时已经没人愿意为迁移排期。
